# 人工服务运营手册（异常转人工闭环）

> 状态说明：本手册中的“已实现”指代码与本地/隔离单测已通过；真实人员与值守安排尚未确认，**不得对外宣称“运营已就绪”**。生产部署与生产迁移需另行授权。

## 1. 配置日常与备用负责人

1. 使用管理员账号进入 `/admin/settings/service-desk`。
2. 日常负责人与备用负责人必须是**两个不同、启用且具备处理权限**的现有员工账号（`exam_reviewer` 或 `admin`）。相同账号、停用账号、无处理权限账号会被后端拒绝。
3. 配置负责人**不会**自动赋予公告发布等业务权限；发布权限仍由原角色决定。
4. 修改会写入 `service_desk_config_audits`（操作人、时间、前后值、原因）。
5. 账号被停用或权限被撤销后，扫描任务会识别失效：日常负责人失效路由到备用负责人；两者都失效进入管理员未分配队列并标记异常。
6. 未配置完整时，后台显示“运营责任人未配置完整”；用户仍可正常提交，任务不会静默丢弃。

## 2. 日常负责人每天检查

1. 打开 `/admin/workbench`，依次查看：待认领、我处理中、待复核、待用户补充、已超时、已升级。
2. “待认领”优先认领，认领只表示有人负责，**不算有效公开响应**。
3. “待复核”表示用户已补充，需继续核对；超过时限仍未处理会进入催办/升级。
4. 按受理编号检索可直接定位用户工单；详情内可打开原业务对象（纠错、公告、扫描件任务或来源告警）。
5. 优先处理“高”优先级：报名截止 72 小时内、涉及资格/时间/取消等重大错误，以及关键采集故障。

## 3. 备用负责人接手

1. 备用负责人在“已升级”或“我处理中（转交给我）”查看被升级任务。
2. 接手必须通过“转交”完成（选择目标账号并填写原因，≥5 字），系统原子更新当前负责人并保留历史。
3. 未经转交不要直接操作他人任务，避免双人同时处理；并发认领/转交只有一方成功，另一方会收到冲突提示。
4. 转交不删除历史、不重置期限、不隐藏超时。

## 4. 补充、核对、关联发布、转交与结案

### 4.1 请求用户补充

1. 详情内点击“请求补充”，必须填写具体问题（例如“请补充毕业证上的完整专业名称”），不能只改状态。
2. 系统将工单置为“待用户补充”，暂停处理更新计时并保存剩余额度，同时向用户发站内通知并深链原工单。
3. 用户在原工单补充后状态进入“待复核”，原负责人收到待办/通知；负责人无效时按日常→备用→管理员未分配路由。

### 4.2 公告补录结案（强门禁）

1. 必须在“结案（公告补录）”中检索并选择**已正式发布、未撤回、未被取代、dataset=real**的公告版本。
2. 用户线索链接与公告链接不同时，必须填写核验依据（≥10 字），后台保留双方来源与审计。
3. 后端会再次校验版本状态（含撤回/取代竞态）；无有效发布结果时拒绝结案，状态保持不变。
4. “已采纳”不等于“已收录”；只有绑定真实发布版本才能标记“已收录”。
5. 历史已收录但缺发布关联的记录显示“发布关联待核验”，不得伪造“查看公告”入口；管理员核验后追加真实关联与审计。

### 4.3 扫描件/解析待人工

1. 必须关联原件、人工提取、证据定位，并交接到**同一快照的审核任务**（填写提取任务 ID 与证据说明）。
2. 扫描件任务完成不等于公告已发布；用户补录仍需等待正式发布。

### 4.4 来源采集异常

1. 恢复类结案：需填写恢复复查、故障窗口与漏采核对/补采结果。
2. 受限/停用（验证码、登录、封禁、永久下线）：不得绕过访问限制；以“受限/停用，已说明”结束排障，必须填写覆盖缺口与替代官方入口；用户侧继续显示受限/未覆盖，**不标记已恢复**。
3. 同一未恢复告警复用活动待办，不重复建任务。

## 5. 故障恢复

### Worker 停止 / Redis 不可用

1. 检查 `/health` 与 Worker 进程日志；Worker 异常时站内催办会暂停，但任务与状态不丢失。
2. 恢复后重新启动 `node dist/worker.js`（与 API 同镜像，独立入口）。扫描任务为 BullMQ 持久化重复任务，重启不会重复轰炸（去重键含任务、阶段/周期、接收人、级别）。
3. 管理员可在工作台手动触发一次扫描（`POST /api/admin/service-desk/scan`，仅管理员），用于补扫；多实例通过 PostgreSQL advisory lock 互斥。

### 通知失败

业务变更、历史与通知在同一事务内写入；通知失败会回滚业务变更或由重试机制补发，不静默丢失。若发现通知缺失，先核对事务日志，再手动补发并记录原因。

### 账号失效

负责人账号停用后，下一轮扫描会识别并路由到备用负责人或管理员队列；管理员应尽快在配置页更换账号。

### 来源受限

按 4.4 处理，不以“暂停”冒充“恢复”；Fixture 仅验证逻辑，不能作为线上恢复证据。

## 6. 时限调整

1. 时限为内部试运行参数（高 2h/8h、中 8h/24h、低 24h/72h + 升级宽限），**不是对用户的办结承诺**。
2. 管理员在配置页修改会生成新版本并留痕；新配置只作用于新阶段，既有期限不被静默改写。
3. 调整依据：近 2—4 周实际首次响应时长、平台处理时长、等待用户时长与积压量；样本不足时不要编造“效率提升”。
4. 提高优先级可提前未到期期限；降低优先级不延长当前周期（后续周期使用新档位）。

## 7. 指标查询

`GET /api/admin/service-desk/metrics`（管理端）提供：

- 待认领、处理中、等待用户、超时、升级、结案数量；
- 按类型与优先级统计首次响应时长；
- 平台实际处理时长（扣除等待用户时间）；
- 等待用户时长；
- 历史缺少发布关联数量。

务必区分“响应”与“解决”、“平台处理”与“用户等待”。

## 8. 隔离演练脚本（E08）

使用 `node scripts/service-desk-sla-drill.mjs`，要求隔离 API、PostgreSQL、Redis、独立 Worker 同时就绪，且 `GET /health` 的 `db/redis/worker` 均为 `up`。启动前把 Worker 扫描间隔缩短（仅隔离环境），例如 `SERVICE_DESK_SCAN_INTERVAL_MS=30000`。

脚本会：配置日常/备用负责人 → 临时缩短三档时限 → 用户提交补录线索 → 到期扫描验证催办与去重 → 升级宽限扫描验证升级 → 旧版本转交 409、新版本原子接手 → 恢复原时限与配置。所需环境变量与前置条件见脚本头部注释。脚本执行失败退出码为 1，环境未就绪为 2。
