## 1. 结论先行

当前版本不应该先做“全国通用爬虫”，而应该在现有公告流水线前后补齐三个深模块：

1. **抓取执行 Module**：定时检查已登记的官方来源，安全下载列表页、公告页和附件，并负责限速、重试、去重与运行留痕；
2. **官网适配 Module**：只描述每个官网“从哪里发现公告、正文和附件”，不负责网络安全、队列、业务字段提取；
3. **文档解析 Module**：把 HTML、PDF、Excel、ET、DOCX 等不同格式统一变成带证据位置的标准文档；
4. **目录投影 Module**：把人工审核通过的数据库版本转成机会匹配可以直接消费的岗位目录。

推荐的当前版本技术组合是：

| 能力 | 当前版本推荐 | 使用原则 |
|---|---|---|
| 定时触发 | `@nestjs/schedule` | 只负责按时间投递任务，不直接执行完整抓取 |
| 后台任务 | `@nestjs/bullmq` + BullMQ + Redis | 抓取、解析和投影在独立 Worker 中执行 |
| 普通网页获取 | Node.js 原生 `fetch` + `AbortSignal` | 统一超时、重定向、域名白名单和响应大小控制 |
| HTML 解析 | Cheerio | 默认方案，适合绝大多数服务端输出的政府网站 |
| JavaScript 页面 | Playwright | 仅作为适配器明确声明的回退能力，不作为默认抓取方式 |
| PDF | `pdfjs-dist` | 提取文本时保留页码；必要时进一步保留坐标 |
| XLS/XLSX/XLSB/ET | SheetJS | 保留工作表、行、列、原始值和展示值 |
| DOCX | Mammoth | 提取段落、标题和表格；不把版式还原当作证据 |
| 扫描 PDF/图片 | 阿里云文档智能或 OCR | 仅在无有效文本层时触发，结果必须待审核 |
| 原始文件 | 本地存储（开发）+ 阿里云 OSS（生产） | 原始快照不可覆盖，生产 Bucket 开启版本控制 |
| 业务数据 | PostgreSQL + Prisma | 继续使用现有数据栈，不另建第二套事实数据库 |

这套方案的重点不是库的数量，而是边界清楚：网络访问只在抓取执行 Module 内发生，官网差异只进入适配器，格式差异只进入文档解析器，匹配页只读取已发布目录。

## 2. 当前实现与缺口

现有代码已经具备以下基础：

- `Source`：官方来源登记；
- `SourceSnapshot`：不可变原始快照与内容哈希；
- `ExtractionRun`：候选字段抽取任务；
- `EvidenceAnchor`：字段证据锚点；
- `ReviewRecord`：人工审核记录；
- `PublishedAnnouncementVersion`：已发布公告版本。

当前主要缺口是：

1. 管理员提交 URL 时，系统保存的仍可能只是 URL 字符串，而不是真实网页内容；
2. 没有定时发现新公告、下载附件和失败重试的执行器；
3. 当前解析器主要面向 HTML/纯文本，没有形成 PDF、表格、Word 和扫描件的统一文档层；
4. 官网差异尚未封装成独立适配器；
5. 数据库中已经发布的公告没有成为机会匹配的唯一数据源，匹配页仍依赖代码中的静态目录。

因此实施顺序必须先打通“真实获取”和“数据库发布进入用户端”，否则继续增加解析格式只会得到更多无法被用户消费的数据。

## 3. 总体数据流

```text

          ▼

          │
          ▼

          │

          ├──URL 规范化与去重
          └──投递 document-fetch 任务
                         │
                         ▼
                 公告页与附件快照
                         │
                         ├──原始字节写入 OSS
                         ├──元数据写入 PostgreSQL
                         └──投递 document-parse 任务
                                          │
                                          ▼
                                  文档解析 Module
                                          │
                                          ▼
                         带页码/单元格位置的标准文档
                                          │
                                          ▼
                               确定性字段抽取 + 可选 AI
                                          │
                                          ▼

```

任何失败都停在对应阶段并可重试，不允许因为一个附件失败而覆盖已有已发布版本。

## 4. 抓取执行 Module

### 4.1 为什么要独立 Worker

网页下载、PDF 解析、表格解析和 OCR 都是慢任务。如果它们直接运行在当前 API 进程中，会带来三个问题：

- 用户请求可能因文件解析占用 CPU 或内存而变慢；
- 进程重启后任务状态难以恢复；
- 无法对某个来源单独限速、暂停或重试。

因此建议在现有 Docker Compose 中增加：

- 一个内部 Redis；
- 一个使用同一后端镜像启动的 `worker` 服务；
- API/定时器只向 BullMQ 投递任务；
- Worker 消费任务并写入 PostgreSQL 和 OSS。

BullMQ 的 Redis 记录是执行状态，不是产品事实。公告、版本、证据和审核记录仍以 PostgreSQL 为准。

### 4.2 任务类型

首版只需要五类任务：

| 任务名 | 输入 | 输出 |
|---|---|---|
| `source.discover` | `sourceId` | 新发现的官方文档 URL |
| `document.fetch` | `sourceId + canonicalUrl` | 不可变 `SourceSnapshot` |
| `document.parse` | `snapshotId` | 标准化文档与解析警告 |
| `announcement.extract` | `snapshotId + parserVersion` | 候选公告、岗位和证据锚点 |
| `catalog.project` | `publishedVersionId` | 匹配服务可读取的已发布目录 |

每个任务都要有稳定幂等键：

- 发现：`sourceId + checkWindow`；
- 下载：`sourceId + canonicalUrl + remoteVersionHint`；
- 解析：`snapshotId + documentParserVersion`；
- 业务抽取：沿用现有 `snapshotId + parserVersion`；
- 投影：`publishedVersionId + projectorVersion`。

重复投递可以发生，但重复写入不可以发生。

### 4.3 调度、重试和限速

建议默认策略：

- 三个首批来源每 30—60 分钟检查一次，来源可单独配置；
- 同一域名并发数默认为 1；
- 请求间隔加入小幅随机抖动，避免所有来源整点同时访问；
- 429、408、502、503、504 进入指数退避，并尊重 `Retry-After`；
- 普通 4xx 不盲目重试；
- 连续失败达到阈值后将来源标记为 `degraded`，暂停自动扩散并通知管理员；
- 验证码、登录和封禁视为人工处理，不做绕过。

### 4.4 安全获取器

所有适配器必须共用同一个 `SafeFetcher`，不能各自直接访问网络。它至少要执行：

- 只允许来源登记中声明的协议与域名；
- DNS 解析后拒绝回环、内网、链路本地和云元数据地址；
- 每次重定向都重新校验目标域名和 IP；
- 限制重定向次数、连接时间、总时间和最大响应体；
- 保存最终 URL、HTTP 状态、ETag、Last-Modified、Content-Type、Content-Length；
- 使用 `If-None-Match` 和 `If-Modified-Since`，304 时不生成新快照；
- 同时检查响应头、文件扩展名和文件魔数，不只相信其中一个；
- 遵守站点 robots 与公开访问规则。

中国政府网站仍可能只提供 HTTP，因此不应简单封死 HTTP；正确做法是仅对已登记官方域名按来源策略放行，并在界面提示其传输安全等级。

## 5. 官网适配 Module

### 5.1 适配器的职责

适配器只回答三个问题：

1. 列表页中哪些链接是招聘公告；
2. 公告页中正文和发布日期在哪里；
3. 公告页中哪些链接是附件、补充公告、延期公告或取消公告。

适配器不负责：

- 发 HTTP 请求；
- 决定重试；
- 写数据库；
- 抽取学历、专业、年龄等业务字段；
- 发布公告。

这样官网 DOM 变化只影响一个适配器，不会把队列、解析和匹配逻辑一起拖坏。

### 5.2 建议 Interface

```ts
interface OfficialSiteAdapter {
  readonly key: string;
  discover(input: ListPageSnapshot): DiscoveredDocument[];
  locateArticle(input: ArticlePageSnapshot): LocatedArticle;
}
```

这里故意不把网络客户端传给适配器。适配器最好是接近纯函数的实现：输入一份已经安全下载的快照，输出结构化定位结果，便于用固定样本做回归测试。

### 5.3 首批适配器

当前真实目录覆盖杭州、宁波和鄞州，建议首批直接建立：

- `HangzhouEducationAdapter`；
- `NingboEducationAdapter`；
- `YinzhouGovernmentAdapter`。

三者共享通用帮助能力：

- 相对链接转绝对链接；
- 去除常见跟踪参数；
- 中文日期解析；
- 附件扩展名和 MIME 判断；
- 标题关键词分类；
- 公告关系候选识别。

不要一开始做一个塞满条件分支的“万能适配器”。可以先提供一个配置型 `HtmlListAdapter` 覆盖结构简单的网站；遇到分页、异步接口或特殊附件再写专用 Implementation。

### 5.4 获取优先级

一个来源应按以下顺序选择能力：

1. 官网公开 RSS、站点地图或公开 JSON 接口；
2. 普通 HTML + Cheerio；
3. 明确需要 JavaScript 才能呈现时，使用 Playwright；
4. 出现验证码、登录或强反爬时，暂停自动化并保留管理员手动提交。

Playwright 应运行在浏览器 Worker 中，并设置很低并发。它不是默认抓取器，因为浏览器的内存、镜像体积和故障面都明显更大。

### 5.5 为什么当前不直接引入 Crawlee

Crawlee 已经提供请求队列、CheerioCrawler 和 PlaywrightCrawler，适合来源很多、需要自动扩展链接和动态切换抓取方式的场景。但当前版本只有三个明确来源，并且还需要 BullMQ 承担附件解析和目录投影任务。

此时直接引入 Crawlee 会形成两套任务队列和两套运行状态，增加理解与运维成本。当前建议是：

- 首版使用 BullMQ 编排全部后台任务；
- HTML 使用 Cheerio，动态页面单独使用 Playwright；
- 当来源达到约 20 个且链接发现策略明显复杂后，再评估把“网页发现子系统”替换为 Crawlee。

这是一个可替换的 Seam，但不需要现在提前实现第二套 Implementation。

## 6. 文档解析 Module

### 6.1 统一输出结构

所有格式最终都输出同一种 `ParsedDocument`：

```ts
interface ParsedDocument {
  snapshotId: string;
  parserVersion: string;
  title?: string;
  blocks: Array<{
    kind: 'heading' | 'paragraph' | 'table-cell' | 'list-item';
    text: string;
    locator: EvidenceLocator;
  }>;
  warnings: string[];
}
```

`EvidenceLocator` 根据格式变化：

- HTML：正文选择器、文本片段与源 URL；
- PDF：页码，必要时增加坐标框；
- Excel/ET：工作表名、行号、列号；
- DOCX：段落序号或表格、行、列；
- OCR：页码、坐标框、识别置信度。

后续业务抽取器只面对 `ParsedDocument`，不需要知道输入原来是 PDF 还是 Excel。这是文档解析 Module 的主要 Leverage。

### 6.2 格式处理策略

#### HTML

- 使用 Cheerio 的 `loadBuffer`，让解析器根据原始字节处理编码；
- 先由官网适配器定位正文容器，再清理导航、页脚和脚本；
- 保存原始 HTML，不只保存清理后的纯文本；
- 附件链接作为子文档进入独立下载和解析任务。

#### PDF

- 使用 `pdfjs-dist` 读取文本层并保留页码；
- 计算每页有效文字密度；
- 文本极少但存在大面积图片时，标记为扫描件并进入 OCR；
- 加密、损坏或字体映射失败时转人工，不伪造结果。

#### Excel、XLS、XLSB 和 ET

- 使用 SheetJS；其官方格式表明确支持读取 WPS ET；
- 保留工作表名、合并单元格、原始值、格式化值、行号和列号；
- 不直接把整张表拼成一段文字；
- 按表头候选识别岗位代码、单位、学科、人数、学历、专业和备注列；
- 表头不稳定时生成候选映射，交给审核人员确认。

#### DOCX

- 使用 Mammoth 转成语义化 HTML；
- 保留标题、段落、列表和表格关系；
- Mammoth 不追求还原复杂版式，因此证据锚点使用段落或表格单元格，不虚构 Word 页码；
- 旧版 `.doc` 暂不在首版内强行自动解析，进入人工处理或后续独立 LibreOffice 转换 Worker。

#### 扫描件和图片

- 仅当 PDF 没有可用文本层或附件本身是图片时进入 OCR；
- 优先选择中国大陆可访问的阿里云文档智能；
- OCR 输出必须保留置信度和坐标；
- 学历、专业、年龄、资格证、报名时间等高影响字段，即使 OCR 置信度较高也必须经过审核；
- 不让大模型替代 OCR 的原文识别职责。

### 6.3 可选 AI 抽取

AI 只应放在标准文档之后，作为复杂自然语言的候选抽取器：

```text
ParsedDocument
  ├──确定性规则：日期、人数、表格列、明确枚举
  └──AI 候选：专业目录解释、例外条款、复杂资格表述
                       │
                       ▼
              结构校验 + 证据完整性校验
                       │
                       ▼
                    人工审核
```

AI 输出必须通过结构 Schema 校验，并为每个高影响字段返回原文锚点。没有锚点时只能显示为“待核对”，不能发布为确定事实。

## 7. 对象存储与快照

开发环境可以继续使用当前 `.data` 目录，生产环境建议切换到私有 OSS Bucket：

- 原始网页、PDF、Excel、DOCX 和图片以内容哈希命名；
- Bucket 开启版本控制；
- 数据库只保存 object key、哈希、MIME、大小、获取时间和 HTTP 元数据；
- 用户端不直接拿永久公开 URL，通过受控接口或短时签名地址查看；
- 设置生命周期策略，原始事实快照长期保留，临时渲染图和中间文件定期清理。

建议建立一个很小的 `ObjectStore` Interface，并提供：

- `LocalObjectStore`：本地开发和测试；
- `OssObjectStore`：生产。

这是已经存在两种真实部署方式的合理 Seam，不是为未来假想需求提前抽象。

## 8. 数据模型调整

### 8.1 扩展 `Source`

建议增加：

- `adapterKey`：使用哪个官网适配器；
- `listUrls`：一个来源可能有多个栏目入口；
- `allowedHosts`：允许抓取与重定向的域名；
- `pollEveryMinutes`、`nextCheckAt`：调度策略；
- `cursor`：页码、最后公告日期或远端游标；
- `etag`、`lastModified`：栏目页条件请求；
- `healthStatus`、`consecutiveFailures`：来源健康；
- `lastCheckedAt`：最近一次检查，不等于最近一次成功发现公告。

### 8.2 新增 `CrawlRun`

保存一次来源检查的业务审计记录：

- 触发方式：定时、管理员、重试；
- 开始、结束、状态；
- 发现数量、下载数量、未变化数量；
- HTTP/适配/解析错误摘要；
- 使用的适配器版本。

不要把 BullMQ 内部任务记录当作长期产品审计数据。

### 8.3 新增 `SourceDocument`

`SourceDocument` 表示一个逻辑上的官方文档，`SourceSnapshot` 表示它在某一时刻的不可变字节版本：

- `canonicalUrl`；
- `kind`：公告页、附件、补充、延期、取消；
- `parentDocumentId`：附件属于哪个公告；
- `relationType`：补充、替代、延期、取消候选；
- `firstSeenAt`、`lastSeenAt`；
- `latestSnapshotId`。

这样同一 URL 内容更新时生成新 Snapshot，而不是制造一个全新的公告身份。

### 8.4 新增 `DocumentParseRun`

不要把“文件格式解析”和“招聘业务字段抽取”混在同一个 `ExtractionRun`：

- `DocumentParseRun`：字节 → 标准文档；
- `ExtractionRun`：标准文档 → 公告与岗位候选。

两者可以独立升级解析器版本、独立重跑，也能更准确地定位失败原因。

## 9. 目录投影 Module

发布不是终点。当前版本必须同时完成以下改造：

1. 建立 `PublishedCatalogRepository`，从 `PublishedAnnouncementVersion` 读取已发布数据；
2. 把数据库结构映射为现有 `RecruitmentAnnouncement` 和岗位单元；
3. `OpportunitiesService` 不再把代码中的静态目录当作生产事实源；
4. 演示数据只能在明确的 Demo 模式中出现，并与真实数据分开；
5. 发布、撤回、延期或取消后重新计算受影响的匹配、日程和提醒。

这个 Module 的完成标准是：管理员发布一条真实公告后，不改代码、不重新构建镜像，用户就能在机会页看到它。

对外只暴露少数 Interface：

- `CrawlOrchestrator.checkSource(sourceId, trigger)`；
- `OfficialSiteAdapter.discover/locateArticle`；
- `DocumentParser.parse(snapshot)`；
- `PublishedCatalogRepository.listPublished()`。

每个 Module 内可以包含限速、重试、编码识别、MIME 判断、页码定位等复杂 Implementation，但调用者不需要知道这些细节。删除其中一个 Module 时，不应迫使其他 Module 大范围重写。

## 11. 管理后台需要同步增加的能力

抓取系统不能成为看不见的黑箱。管理后台应增加：

- 来源健康：正常、延迟、结构变化、被阻止、人工暂停；
- 最近检查、最近成功、下次检查；
- 本次发现/新增/未变化/失败数量；
- “立即检查”按钮；
- 适配器版本和最后一次结构不匹配原因；
- 原始快照、标准文档、候选字段三栏对照；
- 附件解析警告与 OCR 标记；
- 发布后是否成功进入用户端目录；
- 来源连续失败和待审核积压提醒。

## 12. 文件与运行安全

首版至少要落实：

- Worker 使用非 root 用户；
- 文件大小、页数、工作表数量、压缩展开大小和处理时长上限可配置；
- Office/PDF 解析在 Worker 中运行，不在 API 进程中运行；
- 上传或远端附件先经过文件类型检查，条件允许时接 ClamAV；
- ZIP 防止路径穿越和压缩炸弹；首版可以不支持 RAR；
- OCR 和对象存储凭证只放服务端，使用最小权限 RAM 账号；
- 日志不记录用户画像、证件信息和完整密钥；
- 官网抓取只处理公开信息，不绕过访问控制。

## 13. 测试策略

### 13.1 适配器合同测试

为每个官网保存最小、脱敏、可长期测试的 HTML 样本，验证：

- 公告链接发现；
- 相对地址解析；
- 正文定位；
- 附件发现；
- 日期与标题提取；
- 页面结构变化时测试明确失败，而不是静默返回空列表。

### 13.2 安全获取器集成测试

使用本地测试服务器覆盖：

- 301/302 重定向；
- 304 条件请求；
- 429 与 `Retry-After`；
- 超时和超大响应；
- 内网 IP、DNS 重绑定候选和跨域重定向；
- 错误 MIME 与真实文件魔数不一致。

### 13.3 文档黄金样本

至少准备：

- 正常文本 PDF；
- 扫描 PDF；
- 多工作表 XLSX；
- WPS ET；
- 含合并单元格的岗位表；
- 含表格的 DOCX；
- 损坏文件和加密文件。

断言不仅检查“抽到了文字”，还要检查证据是否能定位到正确页码或单元格。

### 13.4 端到端验收

必须有一条完整自动化测试：

```text
测试官网列表页出现新公告
→ 系统发现并下载正文和附件
→ 生成候选字段与证据
→ 管理员审核发布
→ 机会匹配读取数据库版本
→ 用户看到岗位和官方依据
```

另外覆盖同 URL 更新、补充公告、延期、取消、重复任务和发布撤回。

## 14. 分阶段落地

### P0：先闭环，不追求格式齐全

1. 真实 URL 获取与安全校验；
2. 数据库已发布版本接入机会匹配；
3. 增加 BullMQ、Redis 和独立 Worker；
4. 完成一个来源的 HTML 适配器；
5. 跑通“发现—快照—审核—发布—用户端”的端到端链路。

### P1：覆盖现有三个来源

1. 完成杭州、宁波、鄞州三个适配器；
2. 接入 PDF 与 SheetJS；
3. 增加来源健康、失败退避和管理员立即检查；
4. 原始文件切换到 OSS；
5. 灰度运行一周：自动发现和解析，但仍全部人工发布。

### P2：复杂附件与结构变化

1. 接入 DOCX 和按需 OCR；
2. 增加补充、延期、取消关系识别；
3. 增加适配器结构变化告警；
4. 依据受邀用户地区扩到 10—20 个来源；
5. 对复杂资格条款增加 AI 候选抽取，但不自动发布。

### P3：规模化后再评估

- Crawlee 或更完整的网页发现子系统；
- 浏览器 Worker 池；
- 来源分片、优先级与更细的 SLA；
- 双人审核和字段级风险策略；
- 自动回归样本采集与适配器维护工具。

## 15. 当前版本明确不建议

- 不在 API Controller 中同步完成抓取和 PDF/Excel 解析；
- 不为每个官网各写一套网络请求、重试和存储逻辑；
- 不默认使用 Playwright 抓所有网站；
- 不同时引入 BullMQ 队列和 Crawlee 队列；
- 不把所有附件先转纯文本后丢弃页码和单元格；
- 不把 AI/OCR 结果直接发布为资格事实；
- 不在尚未打通数据库目录投影前盲目扩充来源数量；
- 不承诺“全国实时全覆盖”。

## 16. 验收指标

首批三个来源可以用以下指标判断是否达到可试用标准：

- 新公告从官网出现到系统发现的中位时间小于一个检查周期；
- 同一内容重复检查不生成重复快照；
- 来源检查成功率、文档解析成功率分别可见；
- 高影响字段证据覆盖率 100%；
- PDF 页码与表格单元格证据可以回到原文；
- 适配器结构变化不会静默造成“0 条公告”，而会产生健康告警；
- 人工发布后无需重新部署即可进入机会匹配；
- 任何自动任务失败都不影响用户继续查看上一版已审核数据；
- 未覆盖地区明确显示“暂未收录”，不能显示“没有招聘”。
