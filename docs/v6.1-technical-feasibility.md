# 《全国教师公开招聘与备考助手 v6.1》技术可行性与开发方案

> 历史技术/实施记录：保留当时的设计与验证语境，不作为当前需求基线。其中的阶段、章节号和未实现描述仅对应原时间；当前产品要求统一见 [PRD](../PRD.md)，架构与启动见 [README](../README.md)。旧 PRD 可从 Git 历史追溯。

分析日期：2026-10-04  
适用范围：从当前可点击演示版走向 20—50 名真实用户的小范围试用，再逐步扩大覆盖范围。

## 1. 先说结论

这个产品在技术上可以实现，但要把三个层次分开看：

| 目标 | 可行性 | 难度 | 说明 |
|---|---|---:|---|
| 做出能演示完整流程的原型 | 高 | 4/10 | 当前项目已经基本做到 |
| 做出少量地区、20—50 名用户可真实使用的版本 | 高 | 7/10 | 需要真实后端、数据采集、审核、匹配和提醒 |
| 做到“全国、及时、低误判、可追溯” | 可行，但属于长期工程 | 9/10 | 最大投入是数据覆盖与运营，不是服务器性能 |

最难的不是“做页面”，也不是“接一个 AI”。最难的是：

1. 各地公告散落在不同网站，网页和附件格式不统一，还会追加补充公告；
2. 把自然语言条件转换成机器能执行、又能向用户解释的规则；
3. 对学历、专业、应届身份、教师资格、户籍、社保等高影响条件，既不能误判，也不能把“不知道”当成“不符合”；
4. 每个结论都要能回到公告原文、PDF 页码或 Excel 单元格；
5. 全国覆盖不是一次开发完成，而是一项持续的数据运营工作。

因此，正确做法不是先建设一个“全自动全国爬虫”，而是先建设一条“机器采集和提取 + 人工审核 + 版本留痕”的可信数据流水线，再逐渐提高自动化比例。

## 2. 当前项目处在什么位置

当前工作区不是空白项目，已有：

- Next.js 16 + React 19 + TypeScript 的手机端优先前端；
- NestJS + Prisma + PostgreSQL 的后端骨架；
- 计划、重排、证据、纠错、通知、数据治理等前端领域逻辑；
- 41 个前端测试，现有测试全部通过；
- 后端测试与构建可以通过。

但它目前仍然是“高完成度演示版”，不是可正式运营的产品：

- 业务数据主要保存在浏览器 `localStorage`；
- 后端只有基础健康检查和一个很小的用户表；
- 真实登录、公告采集、附件存储、AI/OCR、审核、提醒都没有接入；
- 管理后台是本地 Mock；
- 正式前端构建会请求 Google Fonts，在当前网络环境下失败，生产版应改为自托管字体。

可复用的部分主要是界面组件、计划/重排规则、证据与纠错的产品思路、测试基础。需要重点新建的是后端业务、数据库模型、公告数据流水线和资格匹配引擎。

## 3. 推荐的整体架构

把系统想象成一条有质检员的流水线：

```text
官方网页/附件
      ↓
来源登记与低频采集
      ↓
原始文件永久留档（对象存储 + 内容指纹）
      ↓
网页/Excel/PDF 解析，扫描件再做 OCR
      ↓
AI 按固定字段生成“候选结果”，同时保留原文位置
      ↓
人工审核高影响字段与异常项
      ↓
版本化公告、报考单元、条件和时间节点
      ↓
确定性资格匹配引擎（符合 / 不符合 / 信息不足 / 人工确认）
      ↓
机会列表 → 关注与日程 → 提醒 → 主要目标 → 备考计划
```

这里 AI 像“资料录入助理”，规则引擎像“计算器”，人工审核像“质检员”。不能让 AI 同时兼任三者，否则很难达到 PRD 中“高影响错误为 0”的目标。

## 4. 技术选型，以及为什么这样选

### 4.1 用户端：继续使用 Next.js，而不是立即做原生 App 或小程序

推荐：保留当前 Next.js + React + TypeScript，做响应式手机网页；满足条件后再补小程序。

为什么适合：

- 当前代码、组件和测试可以继续使用，返工最少；
- 用户点开链接即可体验，适合产品还在验证期；
- 公开机会页可以被分享和搜索，原生 App 在这方面更重；
- Next.js 官方支持 Node.js 或 Docker 自托管，不必依赖 Vercel，可部署在中国大陆云服务上；
- TypeScript 可让前后端共享数据结构，减少字段理解不一致。

为什么暂不选其他方案：

- 原生 iOS/Android：体验上限高，但要维护两套客户端，上架、审核和发版成本太高；
- Flutter：可以跨端，但现有 React 页面几乎需要重写，且当前核心风险并不在客户端；
- 只做微信小程序：提醒和触达有优势，但公开链接、搜索、复杂后台和跨平台能力受限。验证出稳定留存后，可以把它作为第二入口；
- 纯静态页面：无法承载真实登录、个性化数据和服务器端安全校验。

生产部署时应使用本地字体和境内静态资源，不让 Google Fonts 等境外资源成为可用性单点。

### 4.2 后端：保留 NestJS，但采用“模块化单体”，不要先拆微服务

推荐：一个 NestJS 业务 API，加一个同仓库的后台 Worker 进程。

模块可以按业务拆为：用户画像、公告与报考单元、证据与版本、匹配、关注与日程、通知、备考、审核与纠错、指标。

为什么适合：

- 与当前 TypeScript 技术栈一致，团队学习和沟通成本低；
- NestJS 对权限、校验、模块边界、任务队列和 OpenAPI 支持成熟；
- 用户量很小时，一个结构清晰的系统更容易改产品逻辑；
- Worker 可以单独扩容，公告解析失败不会拖慢用户页面。

为什么暂不选其他方案：

- Spring Boot：稳定且适合大团队，但当前没有 Java 资产，开发和部署更重；
- FastAPI/Python 全面重写：文档处理生态好，但会放弃现有 TypeScript 代码。只有在真实样本证明解析工具不足时，再增加一个只负责特殊文档的 Python Worker；
- 微服务：会提前引入服务发现、分布式事务、跨服务排错等问题，当前流量和团队规模不需要；
- GraphQL：当前只有一个主要客户端，REST + OpenAPI 更容易调试、缓存、审计和生成接口文档。

### 4.3 数据库：继续使用 PostgreSQL + Prisma，而不是 MongoDB

推荐：PostgreSQL 作为唯一事实数据库，Prisma 负责模型与迁移，复杂报表允许使用原生 SQL。

为什么适合：

- 公告、报考单元、条件、证据、版本、用户、关注、事件之间关系很强，关系型数据库能用外键保护一致性；
- 截止时间、唯一约束、事务、审计记录都适合 PostgreSQL；
- 对少量地方特有字段，可用 `jsonb` 保存，并建立索引；
- 首版搜索以地区、学科、学段、学历、截止时间等结构化筛选为主，PostgreSQL 足够。

为什么暂不选其他方案：

- MongoDB：存不规则 JSON 很方便，但这个产品最重要的是关系一致性和证据链，不是任意文档存储；
- MySQL：也能完成大部分工作，但项目已经使用 PostgreSQL，且 PostgreSQL 的 `jsonb`、约束与扩展更适合“稳定核心字段 + 地方扩展字段”；
- Elasticsearch/OpenSearch：中文全文搜索很强，但需要额外同步、监控和故障处理。首版主要是条件筛选，先不引入；当自由文本搜索质量或数据规模成为真实瓶颈时再添加；
- 向量数据库：资格判断是精确规则问题，不是“意思差不多”问题。向量相似度可在以后辅助找学习资料，不能用于判定能否报名。

### 4.4 原始文件：使用对象存储，不要把 PDF/Excel 塞进数据库

推荐：使用阿里云 OSS（或同等的腾讯云 COS），开启版本控制；数据库只保存文件地址、内容哈希、抓取时间和证据位置。

为什么适合：

- PDF、Word、Excel 和页面快照体积较大，对象存储更便宜、可靠；
- 开启版本控制后，误覆盖或删除时可以恢复；
- 原始文件不覆盖，才能证明“当时系统依据的是哪个版本”；
- 当前已有阿里云部署痕迹，同一云厂商可以减少跨云网络和权限配置。

为什么不放本机磁盘或数据库：

- 本机磁盘随容器迁移或机器故障丢失；
- 数据库保存大文件会让备份、恢复和查询变重；
- 只保存官方链接不够，原站链接可能失效或内容被替换。

### 4.5 后台任务：Redis + BullMQ，而不是 Kafka

推荐：Redis + BullMQ 处理定时采集、文件解析、OCR、AI 提取、变化检测和提醒发送。

为什么适合：

- NestJS 有官方集成；
- 任务可以重试、限速、延迟执行，并放到独立 Worker；
- 当前任务规模属于“后台作业”，不是海量实时日志流。

为什么暂不选其他方案：

- Kafka：适合超大吞吐事件流，但部署和维护成本远超当前需要；
- RabbitMQ：可靠且跨语言友好，但当前主要是 Node.js，BullMQ 更直接；
- 服务器定时脚本：很难统一查看重试、失败原因、重复执行和执行进度。

每个任务仍需有数据库中的业务状态和幂等键，不能只依赖队列。“同一公告同一版本”“同一用户同一提醒”都必须防重复。

### 4.6 文档解析：固定解析器优先，OCR 兜底，AI 辅助，人工发布

推荐顺序：

1. HTML、Excel 等有结构的内容先用确定性解析器；
2. 有文本层的 PDF/Word 直接抽取；
3. 扫描件才调用 OCR/文档智能服务；
4. AI 按 JSON Schema 把文本转换为候选字段；
5. 高影响字段在发布前人工审核。

阿里云文档智能目前支持 PDF、Office、图片等多种格式的结构化解析；百炼模型支持按 JSON Schema 输出固定结构，适合作为候选提取工具。但“输出格式正确”不等于“内容一定正确”，因此必须验证原文位置和人工复核。

为什么不选“全部交给大模型”：

- 同一份公告重复运行可能得到不同答案；
- 细小的“且/或”“仅限”“须在某日期前取得”等词会直接改变资格；
- 大模型容易给出看似合理但原文没有的补充；
- 一旦用户投诉，很难仅靠提示词解释当时为何这样判断。

为什么不立即自建 OCR/大模型：

- 小规模试用时，云 API 的启动速度和总成本通常更合适；
- 自建需要 GPU、模型升级、监控和精度调优；
- 应先用真实公告做对照测试，确定调用量、精度和数据合规要求，再决定是否自建。

所有 OCR 和大模型供应商都应放在“适配器”后面，避免业务代码绑定一家厂商。

### 4.7 AI 的正确边界

适合 AI 的工作：

- 从公告中提取候选字段和原文片段；
- 对补充公告生成“发生了什么变化”的草稿；
- 把已确认的考试内容改写成用户易懂的说明；
- 在规则确定任务模块与时长后，润色学习任务文案。

不适合直接交给 AI 的工作：

- 最终判断用户一定能报名；
- 决定专业是否属于某官方目录；
- 推测缺失的时间、用工性质或招聘人数；
- 自动发布没有证据位置的高影响字段；
- 预测上岸概率。

资格匹配本身不需要 RAG 或聊天机器人，应由确定性规则执行。RAG 可以在以后用于“根据已审核公告回答问题”，回答时仍必须展示来源。

### 4.8 部署：境内云 + 托管数据库，暂不使用 Kubernetes

推荐的小范围试用部署：

- 一台或两台境内云服务器运行前端、API 和 Worker 容器；
- 托管 PostgreSQL；
- 托管 Redis；
- OSS 保存原始公告与附件；
- 负载均衡/Nginx 负责 HTTPS、限流和请求大小限制；
- 云日志服务记录错误和任务状态；
- 备份与恢复演练，而不只是“打开自动备份”。

为什么不继续把正式版完全放在 Vercel/Supabase 等境外平台：

- 面向中国大陆用户时，访问速度、网络稳定性、备案和个人信息流向更难控制；
- 当前前端可以用 Docker 自托管，不会失去 Next.js 的核心能力。

为什么不用 Kubernetes：

- 20—50 名试用用户不需要它；
- 它解决的是大规模容器调度问题，却会先增加部署、监控和排障复杂度；
- 等到服务数量、团队规模和发布频率真正需要时再迁移。

## 5. 资格匹配应该怎样实现

这是产品的核心壁垒，应单独做成可测试的规则模块，不能散落在页面代码里。

### 5.1 四值判断，而不是简单的“是/否”

每一项条件只返回四种状态：

- `PASS`：现有事实明确满足；
- `FAIL`：现有事实明确不满足；
- `UNKNOWN`：缺少用户信息或公告信息；
- `MANUAL_REVIEW`：专业目录、应届定义等存在歧义，需要人工确认。

总结果规则：

- 任一硬条件为 `FAIL`，结果为明确不符合；
- 没有 `FAIL`，但存在 `MANUAL_REVIEW`，显示建议人工确认；
- 没有前两者，但存在 `UNKNOWN`，显示补充信息后判断；
- 全部关键条件为 `PASS`，才显示初步符合。

这样天然符合 PRD 中“未填写不得显示为不符合”的要求。

### 5.2 每条判断都保存五样东西

1. 判断的是哪项条件；
2. 使用了用户的哪条事实；
3. 使用了公告的哪条要求；
4. 执行了哪个版本的规则；
5. 原文证据位于哪个网页段落、PDF 页码或 Excel 工作表/单元格。

用户看到的是易懂解释，后台保存的是完整计算记录。公告或用户画像变化时，只重新计算受影响的结果。

### 5.3 专业匹配不能只做字符串包含

应按以下优先级处理：

1. 公告明确列出的专业全称/代码精确匹配；
2. 公告引用的官方专业目录，并记录目录名称、版本和层级；
3. 经审核的别名和历史更名；
4. 仍有歧义时进入人工确认。

语义相似度或大模型可以提示审核员“可能相关”，但不能直接把相近专业判定为符合。

## 6. 公告数据流水线应该怎样做

### 6.1 建立“来源登记表”，不要一开始全网乱爬

每个官方来源记录：主管单位、地区、入口页、栏目规则、允许的采集方式、robots 状态、合理访问频率、最近成功时间、失败原因和负责人。

采集器必须：

- 使用明确的 User-Agent 和联系方式；
- 遵守 `robots.txt` 与站点使用规则；
- 低频、错峰、缓存，优先使用 `ETag`/`Last-Modified`；
- 不绕过验证码、登录或反爬限制；
- 发现受限站点时改成人工录入或寻求正式数据合作；
- 对每个域名设置并发和频率上限。

《网络数据安全管理条例》第十八条明确要求使用自动化工具访问、收集网络数据时评估对网络服务的影响，不得非法侵入或干扰服务。`robots.txt` 是应遵守的抓取偏好协议，但它本身不等同于法律授权。

### 6.2 原始数据永不直接覆盖

每次抓取保存：

- 官方 URL、抓取时间、HTTP 状态与响应头；
- 页面快照和全部附件；
- SHA-256 内容指纹；
- 与上一版本的差异；
- 原公告、补充公告、取消公告之间的关系。

解析结果进入“待审核区”，审核通过后才进入用户可见的正式数据。补充公告不是新建一份互不相关的数据，而是对原版本做有来源的变更。

### 6.3 先做有代表性的地区样本

建议首轮选择 3—5 个招聘方式明显不同的地区，覆盖：直接报学校、区县岗位组、录取后择校、事业编和地方正式用工形式。先积累约 100 份真实公告及附件的“标准答案集”，再扩大来源。

“全国”可以是产品定位和可扩展的数据模型，但试用期页面必须明确展示实际覆盖地区、来源数量和最后更新时间。

## 7. 推荐的开发顺序

### 阶段 0：两周技术验证

目标不是做更多页面，而是验证最难的部分。

- 选取 30—50 份不同格式的真实公告和岗位表；
- 验证 HTML、PDF、扫描 PDF、Word、Excel 的解析成功率；
- 定义公告、报考单元、条件、证据和版本的数据模型；
- 人工标注一份小型标准答案集；
- 做一个从原文件到审核后台的纵向样例；
- 确定每份公告平均人工审核时间。

如果这一步做不通，不应继续扩大用户端功能。

### 阶段 1：真实机会与审核后台，约 4—6 周

- 来源登记、采集、原始文件留档；
- 文档解析、OCR、AI 候选提取；
- 审核、版本、补充公告、失效和纠错；
- 真实 PostgreSQL 与对象存储；
- 先让运营人员稳定产出可信公告数据。

### 阶段 2：画像、资格匹配和关注，约 4—5 周

- 访客基础画像和登录迁移；
- 四值资格匹配与逐项解释；
- 机会列表、详情、关注状态；
- 服务端认证、权限、审计和数据删除；
- 埋点计算基础画像完成率、有效机会率和关注率。

### 阶段 3：时间线和真实提醒，约 2—3 周

- 报名、审核、缴费、准考证、考试等事件；
- 重复提醒防护、变更影响分析；
- 先做站内提醒，再根据真实用户需求接短信或微信；
- 短信只用于高价值节点，并处理签名、模板审核和发送回执。

### 阶段 4：备考闭环，约 3—4 周

- 复用现有计划、反馈和重排规则；
- 用已审核的考试内容作为计划输入；
- 快速自评、短诊断、首个 7 天计划；
- AI 只负责文案辅助，时长、门禁和内容范围由规则控制；
- 验证首项学习任务开始率和 7 日有效目标推进率。

以上可部分并行。以 4—6 人的完整小团队计算，12—18 周可形成可信的小范围试用版；一名全栈开发者独立完成，通常应按 6—10 个月估算，而且仍需要产品/招聘政策审核人员持续参与。全国覆盖没有一次性的“完成日期”。

## 8. 建议团队配置

- 1 名产品负责人兼领域规则负责人；
- 1 名前端工程师；
- 1 名后端工程师；
- 1 名数据采集/文档处理工程师；
- 1 名测试或质量工程师，可前期兼职；
- 1—2 名公告审核与教师招聘政策运营人员。

后两类角色很重要。这个产品不能只靠程序员和模型完成，因为“什么算正确”需要领域人员建立标准答案和处理歧义。

## 9. 上线前必须达到的技术质量线

### 数据与匹配

- 高影响字段未经人工审核，不进入“初步符合”；
- 每个高影响字段有原文证据位置；
- 已截止机会不再作为可报名机会；
- `UNKNOWN` 永远不能被默认转成 `FAIL`；
- 补充公告能触发受影响匹配和提醒重算；
- 用一批人工标注公告持续做回归测试。

### 安全与隐私

- 正式账号使用手机验证码或微信登录，不沿用演示账号；
- 所有管理权限在服务端校验，隐藏按钮不算权限控制；
- TLS、数据库加密、最小权限、操作审计、备份恢复；
- 用户画像与公告公共数据分开；
- 删除账号时，私有数据删除，公共证据保留，审计记录匿名化；
- 匹配可以完全在自有后端执行，不把用户完整画像发送给大模型；
- 如果学习计划调用模型，只发送完成任务所需的最少信息，并明确告知。

《个人信息保护法》要求目的明确、最小范围、公开透明，并保障用户查询、更正和删除等权利。正式对外前，还应完成隐私政策、个人信息清单、第三方 SDK/供应商清单、保存期限、账号注销流程和个人信息保护影响评估。本文不是法律意见，生成式 AI、自动化决策、备案与教育类服务边界应在上线前由合规人员复核。

资格过滤、个性化排序和推荐也应按算法推荐风险来设计：公开基本排序逻辑，提供不使用个人画像的普通搜索/筛选入口，允许关闭个性化、调整偏好、删除用户标签，并保留申诉和人工复核入口。是否达到算法备案或安全评估条件，需要结合正式业务形态和规模专项确认，不能简单理解为“用了排序就一定备案”或“用了规则就完全不受约束”。

如果向用户展示 AI 生成的学习计划、公告摘要或通俗解释，应清楚标注“AI 生成/AI 辅助”，同时展示其依据；下载、复制和导出时也要评估生成合成内容标识要求。AI 文本与“官方事实/人工审核结论”必须使用不同状态呈现。

在中国大陆服务器公开上线前，应准备 ICP 备案；若未来加入付费会员、广告或课程，还要重新核验经营许可。产品是否涉及需要前置审核的教育互联网信息服务，应按实际功能向属地主管部门确认，而不是只依据产品名称自行判断。

### 可运维性

- 采集、解析、审核、发布、通知都有可查询状态；
- 失败任务自动重试但有上限；
- 同一任务有幂等键，重复执行不会制造重复数据；
- 关键指标、错误率、积压量和最后成功采集时间有告警；
- 能把单个错误结论撤回，并列出受影响用户、机会、提醒和计划。

## 11. 当前工程中应先处理的两个基础问题

1. 当前工作区根目录不是 Git 仓库。进入真实开发前，应建立私有版本库、分支和发布流程，避免多人协作和回滚失控。
2. `deploy` 目录下出现了看起来像私钥和内部令牌的文件名。未读取其内容，但这类凭据不应与项目文件放在一起；应立即确认是否仍有效，必要时轮换，并改用云 Secret Manager/环境变量注入，同时加入忽略规则和泄漏扫描。

## 12. 最先做的十件事

1. 冻结 v6.1 的 P0 字段字典和四值匹配规则；
2. 建立私有 Git 仓库和密钥管理；
3. 收集 30—50 份代表性公告做解析验证；
4. 定义公告、报考单元、条件、证据、版本的数据库模型；
5. 完成原文件留档和审核后台的第一条真实流水线；
6. 用人工标准答案测解析与匹配，不按“看起来不错”验收；
7. 把现有前端服务层逐步替换为真实 REST API；
8. 实现资格匹配与逐项解释，再做排序；
9. 接入关注、时间线和站内提醒；
10. 达到 20—50 人试用的数据质量后，再接备考闭环和扩大地区。
