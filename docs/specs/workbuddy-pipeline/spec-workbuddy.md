# WorkBuddy 规格：公告/岗位提取与审核契约

> 状态：WB0 已定义，WB1–WB6 未实现。
> 本文只规定“什么算正确”。实现细节（抽取器、存储、审核界面）由后续模块完成。

## 1. 范围定义

### 1.1 `announcement`（公告公共范围）

公告级事实：只出现一次、对整份公告成立、不属于任何单个岗位的字段。

| 字段族 | 说明 |
|---|---|
| 公告标识 | 公告标题、发布主体、官方 URL、公告编号、发布/更新日期 |
| 批次信息 | 报名起止时间、报名截止时点、缴费时间、笔试/面试时间（若公告统一） |
| 统一规则 | 统一适用的年龄基准日、统一年龄例外、统一材料清单、统一报名入口 |
| 用工性质 | 若公告全文统一（如“本次招聘均纳入事业编制”），属于公共；否则属于岗位 |

### 1.2 `job`（岗位范围）

岗位级事实：随岗位变化、每个岗位独立成立、可能跨岗位不同的字段。

| 字段族 | 说明 |
|---|---|
| 岗位标识 | 岗位编号/代码、单位名称、招聘岗位名称 |
| 岗位属性 | 学段、学科、招聘人数、编制/用工性质（岗位各自时） |
| 岗位资格 | 学历、学位、专业、教师资格、年龄、户籍、工作经历（岗位各自时） |
| 岗位去向 | 分配方式、任教学校/学段（录取后择校等场景） |

### 1.3 归属判定原则

- 一个字段只能归属 `announcement` 或某 `job` 之一，不允许同时归属两者；
- 归属判定以**原文结构**为准：出现在公告公共条件块/统一规则段落 → `announcement`；
  出现在岗位表某行/岗位明细段落 → 对应 `job`；
- 原文结构无法判定归属时 → 标记为 `scope: "unknown"`，进入人工审核，**不得猜归属**；
- 同一份公告中的不同岗位若字段值不同，必须各自独立归属，不得用首行值覆盖其余行。

## 2. 稳定岗位标识（stable job identity）

### 2.1 目标

同一岗位在“抽取 → 审核 → 发布 → 用户匹配”全链路中使用同一稳定标识，
保证：补充/更正公告能回连到原岗位；跨版本差异可对齐到岗位；用户关注能精确到岗位。

### 2.2 生成原则

岗位标识由**公告内可定位的稳定键**派生，优先级从高到低：

1. **官方岗位编号/代码**（原文明确给出，如“岗位代码 3301A01”）→ 主键；
2. 无官方编号时，用**公告标识 + 岗位出现位置**（工作表名 + 行号，或正文段落锚点）生成**位置键**；
3. 位置键在“岗位行增删”时可能漂移，因此**位置键只作为候选标识**，必须经人工审核确认后才能固化为正式 `jobId`；
4. 任何岗位标识一经发布，在后续版本中**不得重编号**（保持稳定）；新增岗位只能追加新标识。

### 2.3 不变量

- `jobId` 在公告内唯一；
- `jobId` 一旦 `published`，跨版本保持不变；
- 候选阶段可用 `jobKey`（含来源信息）表达“尚未固化”的岗位，发布时须映射到稳定 `jobId`。

## 3. 候选字段契约（CandidateField）

每个候选字段至少包含以下结构（在现有 `CandidateField` 基础上**扩展**，非破坏）：

| 字段 | 类型 | 必需 | 说明 |
|---|---|---|---|
| `field` | string | 是 | 字段名，取值见 `field-catalog.md` |
| `value` | string | 是 | 原文提取/标准化后的值（可能含替代值列表） |
| `status` | enum | 是 | `extracted` / `unknown` / `conflict`（见 §4） |
| `scope` | enum | 是 | `announcement` / `job` / `unknown`；`job` 时必须带 `jobKey` |
| `jobKey` | string? | 条件 | `scope=job` 时必填，指向岗位标识 |
| `ruleVersion` | string | 是 | 产生该字段的规则/解析器版本（可审计、可回放） |
| `evidence` | anchor[] | 条件 | 高影响字段必填；`conflict` 时必须 ≥ 2 条，各自标注来源 |
| `alternatives` | value[] | 条件 | `conflict` 时的替代值列表（含各自证据），不得静默覆盖 |
| `origin` | enum | 否 | `rule` / `ai` / `ocr`（沿用现有约定） |
| `confidence` | number? | 否 | 0–1，仅展示，不替代人工审核 |
| `needsHumanConfirm` | bool | 否 | AI/OCR 或低置信度时为 true |

### 3.1 替代值（alternatives）

`conflict` 状态的字段必须携带 `alternatives` 数组，每一项是：

```
{ value: string; source: { kind; locator; excerpt }; selectedBy?: "ai" | "human" }
```

- 冲突时保留**所有值及其证据**，不允许在无人工干预下选一个丢弃另一个；
- 人工审核选定后，`value` 更新为选定值，`alternatives` 保留为审计留痕。

## 4. 三种提取状态（status）

| 状态 | 含义 | 规则 |
|---|---|---|
| `extracted` | 成功提取到一个值 | 带证据；可进入审核 |
| `unknown` | 原文未写明 / 无法判定 | **未知 ≠ 不符合**。不产生判定结论，不进入“不符合”分类；下游匹配遇 unknown 走“补充后判断/人工确认”，不得判 FAIL |
| `conflict` | 同一字段存在两个及以上互相矛盾的值（如正文与附件不一致） | **禁止静默覆盖**。必须同时保留全部值与各自证据，进入人工审核 |

### 4.1 状态转移

```
extracted ──人工审核──► adopt / edit / reject（见 §5）
unknown   ──补充信息──► extracted 或 保持 unknown（不得自行推断为不符合）
conflict  ──人工裁决──► edit（选定其一并留痕）或 pending
```

## 5. 人工处理结果（四种）

| 结果 | 含义 | 规则 |
|---|---|---|
| `adopt` | 采纳候选值 | 用于 `extracted`；写入审核人与时间 |
| `edit` | 修改后采纳 | 记录修改前后值；`conflict` 裁决后必须 `edit`（选定并留痕） |
| `reject` | 驳回该字段 | 字段不进入发布载荷；原因必填；可重新提取 |
| `pending` | 待补充/待确认 | 字段保留在待审核队列；`unknown` 或证据不足时用 |

### 5.1 AI/OCR 候选

- `origin = ai | ocr` 的字段**仍需人工确认**（`needsHumanConfirm`），
  无人工确认时间不得发布（与现有 `findUnconfirmedAutoFields` 一致）；
- 确定性规则字段同样需要人工审核通过，只是不强制“逐字段人工确认时间”。

## 6. 两阶段载荷契约（禁止混用）

候选载荷与发布目录载荷是**两个阶段、两种契约**，任何实现都不得混用。

| 维度 | 候选载荷（阶段一） | 目录载荷（阶段二） |
|---|---|---|
| 结构 | `ExtractionCandidate`（`{fields, parserVersion, rawJson}`，字段为 §3 契约） | `RecruitmentAnnouncement` → `AnnouncementVersion` → `ApplicationUnit`（含 `{dataset, announcement, version}` 语义） |
| 字段粒度 | 扁平候选字段，可 `unknown` / `conflict` / `alternatives` | 结构化、可匹配的最终值（unit 有稳定 `id`、`requirements` 有 `criterion`） |
| 岗位归属 | 用 `scope` + `jobKey`（候选，未固化） | 用稳定 `unit.id`（已发布） |
| 产生时机 | 解析/AI/OCR 后 | 人工审核并发布后 |
| 下游 | 只进审核界面 | 只进匹配、日程、用户端 |

### 6.1 转换边界

- 候选 → 目录的转换**只能发生在审核通过、发布动作之后**；
- 转换必须显式、可校验：每个目录字段能回溯到至少一个已 `adopt/edit` 的候选字段及其证据；
- `unknown` / `conflict` / `pending` 状态的字段**不得**进入目录载荷；
- 目录载荷必须带 `dataset` 标记（生产 `real` / 测试 `test`），与现有三层事实分离一致。

## 7. 红线汇总（实现不得违反）

1. 未知（`unknown`）不等于不符合，不得把 unknown 判为 FAIL；
2. 冲突（`conflict`）不允许静默覆盖，必须保留全部值与证据；
3. AI/OCR 候选仍需人工确认，不得自动发布；
4. 候选载荷与目录载荷是两阶段契约，禁止混用；
5. 岗位字段必须稳定归属到岗位（`scope=job` + `jobKey`），不得用首行值代表全表；
6. 高影响字段无证据锚点不得通过审核（沿用现有规则）。
