# 教招有据 UI/UX 改版详细方案

版本：v1.2 设计与技术实施稿
日期：2026-10-13
适用范围：首页、首次资格预筛、结果页、岗位卡片、定向补充信息闭环、官方公告数据闭环及其桌面端/移动端响应式布局
状态：已确认设计方向，尚未代表代码已经实现

> 本文整合 2026-10-12 至 2026-10-13 的连续讨论与原型结论，用于后续视觉设计、产品评审、开发拆解和验收。若本文与更早的 UI 发散稿冲突，以本文为准；产品事实、资格规则和数据可信度仍分别遵循 v7.1、v7.0 与国内网络基线。最新用户决策优先于旧版流程安排。

> **v7.2 交接说明：** 本文与主动抓取、附件解析方案已经合并到仓库根目录的 [《PRD：教招有据 v7.2 决策体验与可信机会闭环》](../PRD-教招有据-v7.2-决策体验与可信机会闭环.md)。后续 Coding 工具应以 v7.2 PRD 为实施主文档；本文保留为 UI/UX 研究与细节来源。

## 1. 改版结论摘要

本轮改版不以“增加更多功能”为目标，而是把产品从一个解释较多、入口与结果并列展示的页面，收敛为一个以用户决策为中心的工具。

最终方向概括为：

> 首页先让用户看到结果价值，填写流程一次收齐会影响筛选的基础信息，结果页只回答“哪些岗位值得看、为什么、在哪里、什么时候截止、下一步做什么”。

已经确认的主要决策如下：

1. 首页采用“结果先行”方案，不再展示长篇虚构示例。
2. 首页首屏只有一个高强调主操作：“开始匹配岗位”或“开始资格预筛”。
3. 用工形式偏好移入首次填写的第二屏，不在用户看结果时再次提问。
4. 结果页的“优先机会 / 补充后判断 / 偏好范围外”是互斥分类，点击后只显示该分类内容。
5. 地点与地图入口紧跟岗位名称出现，不再藏在展开区或详情深处。
6. “查看官方依据”和“保存机会”使用相同高度、圆角和对齐方式，但保留主次视觉层级。
7. 岗位卡不再把全部字段等权展示，而是突出岗位、地点、截止时间、判断状态和一个关键风险。
8. 桌面端扩大页面舞台并利用横向结构；移动端保持单列，不把桌面布局机械缩小。
9. 真实数据、系统判断和虚拟示例必须具有清楚边界。
10. 页面维持“可信的未来感”，不采用过度炫技的霓虹、重玻璃拟态或数据大屏风格。
11. 官方公告必须从“代码内置样本”转向“来源登记、真实抓取、人工审核、数据库发布、用户端消费”的闭环；不以未经核验的数据量作为成功指标。

## 2. 为什么需要改版

### 2.1 首页的问题：用户先看到了一份说明书

当前首页右侧示例同时展示主要依据、待确认事项、官方来源、核对时间和免责声明。这些信息对于证明产品能力有价值，但在首页首屏全部展开，会出现三个问题：

- 它与主标题和“开始资格预筛”争夺注意力；
- 用户还没有产生兴趣，就要阅读一段接近岗位详情的信息；
- 用户需要先理解示例结构，才能理解产品价值。

首页的任务并不是完整教育用户，而是在 5—10 秒内回答：

1. 这个产品能帮我做什么？
2. 我能得到什么样的结果？
3. 我现在应该点哪里？

因此首页应该展示“结果的形状”，而不是展示“结果的全部内容”。

### 2.2 填写流程的问题：收集与回答发生了混杂

用户完成个人信息后，在结果出现之前又被询问“想看哪类用工形式”。这会让用户产生一种感受：明明已经填完，为什么还不能看到答案？

用工形式虽不是资格条件，却会直接影响筛选与排序。它应该和地区偏好一样，在生成结果前完成。最新用户决策因此覆盖 v7.1 中“首次画像不收集用工偏好”的旧安排：第二屏使用三档紧凑选择，允许暂不确定，并明确它只影响筛选与排序，不影响资格判断。

### 2.3 结果页的问题：信息齐全，但答案不够突出

原有结果页同时承载覆盖说明、筛选、示例解释、岗位信息、画像摘要、真实性说明和后续入口。每个模块单独看都有合理性，但叠加后会让用户难以迅速回答：

- 我到底有几个优先机会？
- 哪一个最值得先看？
- 为什么系统认为我可能符合？
- 我还缺哪一项信息？
- 岗位在哪里？
- 什么时候截止？

改版重点不是继续删字段，而是建立明确的信息层级和逐层披露关系。

### 2.4 桌面端的问题：移动卡片被放进了大屏幕中央

当前原型的主体宽度偏窄，适合移动端或窄窗口，但在 1440px 以上的桌面屏幕中会产生“大面积空白包围一条窄内容”的感觉。

解决方法不是把文字行无限拉长，也不是让每张卡铺满整屏，而是：

- 让页面背景、分区和视觉舞台覆盖更完整的横向空间；
- 将正文容器扩大到约 1200—1280px；
- 使用 12 栏网格重新组织横向关系；
- 将卡片内部从纵向堆叠改为桌面双区布局；
- 在移动端恢复单列阅读顺序。

## 3. 本轮设计原则

### 3.1 结果先于解释

用户先看到结论数量、最优岗位和关键风险，再决定是否打开完整依据。首页、结果页和岗位卡都遵循这一顺序。

### 3.2 一个页面只推动一个主动作

- 首页：开始匹配岗位；
- 填写第一屏：进入资格填写；
- 填写第二屏：查看匹配结果；
- 初步符合岗位：查看官方依据；
- 待补岗位：补充一项信息；
- 偏好范围外岗位：查看或调整偏好。

保存、返回、修改和查看说明是次级动作，不应与主动作同等强调。

### 3.3 状态必须改变内容，而不只是改变颜色

“优先机会 / 补充后判断 / 偏好范围外”不是三个静态标签。切换后必须改变下方数据集，且分类互斥。

### 3.4 同一几何系统，不等于同一视觉权重

相邻按钮应该具有一致的高度、圆角、字体基线和触控面积，但主要操作使用实心样式，次要操作使用描边或弱化样式。统一解决杂乱，层级解决决策。

### 3.5 事实、判断、偏好严格分开

- 官方事实：公告内容、地点、人数、截止时间；
- 系统判断：初步符合、待补信息、建议确认、明确不符；
- 用户偏好：地区、用工形式；
- 未知状态：公告未明确或用户尚未填写。

偏好范围外不能被写成资格不符合，未知也不能被写成不符合。

### 3.6 桌面端利用空间，移动端保护顺序

响应式不是整体缩放。桌面端通过并列关系提高扫描效率；移动端按“状态—岗位—地点—条件—行动”的顺序堆叠。

## 4. 新的信息架构与用户流程

```text
首页：结果价值 + 唯一主入口
  ↓
第一屏：地区意向
  ↓
第二屏：基础资格 + 用工偏好
  ↓
结果页：分类结果工作台
  ├─ 优先机会
  ├─ 补充后判断
  └─ 偏好范围外
  ↓
岗位详情：完整条件、官方证据、版本与报名动作
  ↓
保存后：统一日程与报考推进
```

职责边界：

- 首页负责让用户产生兴趣并开始；
- 填写页负责收集影响结果的信息；
- 结果页负责比较和决定先看什么；
- 详情页负责证明判断；
- 日程页负责继续推进。

## 5. 首页详细方案：结果先行

### 5.1 首页首屏结构

桌面端采用左右分栏：

```text
┌──────────────────────────────────────────────────────────────┐
│ 教招有据                                               登录  │
├──────────────────────────────────────────────────────────────┤
│ 30 秒完成资格预筛        │ 结果预览 · 示例                   │
│                          │ [1 优先] [2 补充] [3 偏好外]       │
│ 哪些教师岗位，           │                                  │
│ 你现在就能报？           │ 杭州某公办初中 · 语文教师         │
│                          │ 杭州 · 余杭区   地图 ↗             │
│ 简短价值说明             │ 3 项已通过 · 户籍待确认            │
│ [开始匹配岗位 →]         │ [查看官方依据]                    │
│ 无需登录 · 约 30 秒      │                                  │
│ 真实公告 · 可核对 · 不瞎猜│                                  │
└──────────────────────────────────────────────────────────────┘
```

### 5.2 推荐文案

眉题：

> 30 秒完成资格预筛

主标题：

> 哪些教师岗位，你现在就能报？

副标题：

> 填写地区、专业和教师资格，我们直接给出优先机会、待补信息和官方依据。

主按钮：

> 开始匹配岗位

辅助信息：

> 无需登录 · 约 30 秒

信任短句：

- 真实公告；
- 逐条可核对；
- 不确定就明确提示。

### 5.3 结果预览应该保留什么

保留：

- 三类结果及数量；
- 一条岗位名称；
- 地点和地图入口；
- 截止紧迫度；
- “3 项已通过 / 1 项待确认”；
- 一个“查看官方依据”动作。

删除或后置：

- 大段“主要依据”；
- 大段“待确认事项”；
- 官方来源的解释段落；
- 最后核对时间的完整定义；
- 重复免责声明；
- 与主按钮同权重的“先看结果示例”大按钮。

结果预览仍需标注“示例”，但只需一个页面级标识，不应在每个字段反复强调。

### 5.4 首页桌面端布局

- 页面视觉背景可以铺满可用宽度；
- 内容容器宽度建议 `min(1280px, 100% - 64px)`；
- 12 栏网格，左侧文案约 5 栏，右侧结果预览约 7 栏；
- 两侧最小留白 32px，大屏幕不建议小于 48px；
- 主标题最大行宽约 9—11 个汉字，不随屏幕无限增长；
- 结果预览可以更宽，但不增加更多字段；
- 首屏控制在常见桌面视口内完整看到标题、按钮和主要预览。

### 5.5 首页移动端布局

顺序调整为：

1. 品牌与登录；
2. 眉题、标题和副标题；
3. 主按钮；
4. “无需登录 · 约 30 秒”；
5. 简化结果预览；
6. 三条信任短句。

移动端结果预览不展示完整三列统计卡，可以使用一行可横向排列的数字摘要。主按钮占满可用宽度，最小高度 48px。

## 6. 两屏资格填写方案

### 6.1 第一屏：地区意向

主问题：

> 你想优先查看哪里的教师招聘？

交互顺序：

1. 先显示地区搜索；
2. 显示当前已覆盖的常用地区；
3. 选择地区后设置“只考虑 / 优先考虑 / 也可以考虑”；
4. 提供“还没想好，先看覆盖范围”；
5. 主按钮为“下一步：填写报考条件”。

页面不出现岗位结果，也不提前解释所有匹配规则。

### 6.2 第二屏：基础资格与用工偏好

字段按用户理解顺序排列：

1. 最高学历；
2. 毕业时间；
3. 专业全称；
4. 教师资格状态；
5. 教师资格学段和学科；
6. 用工形式偏好。

用工形式使用三档：

- 只看事业编；
- 事业编优先，也看其他官方岗位；
- 暂不确定，先全部看看。

说明文案：

> 该选择只影响结果的筛选与排序，不影响资格判断。

底部在主按钮前显示一行结果条件摘要：

> 杭州优先 · 本科 · 汉语言文学 · 初中语文 · 事业编优先

主按钮：

> 查看匹配结果

### 6.3 为什么把用工偏好放在这里

- 它直接影响用户想看到哪些岗位；
- 在生成结果前收集，能避免结果页再次中断；
- 三档选择比平铺备案制、员额制、控制数等概念更容易理解；
- “暂不确定”降低填写压力；
- 明确它不是资格条件，可以避免误解。

## 7. 结果页详细方案

### 7.1 顶部结果摘要

标题不再使用笼统的“为你找到 3 个值得看的机会”，而是直接表达分类：

> 1 个优先机会，2 个补充后可判断

副标题：

> 优先机会已按资格状态与报名截止时间排序。

右侧展示：

> 最后核对：2026 年 10 月 13 日

“偏好范围外”的数量不进入“值得看的机会”总数，避免把低优先级结果包装成核心机会。

### 7.2 当前条件摘要

不要把学历、专业、学科、地区全部做成五六个胶囊。建议：

```text
当前条件  杭州优先 · 本科 · 汉语言文学 · 初中语文
[事业编优先，也看其他]                              修改条件
```

只有用工偏好保留为可识别的筛选胶囊，其余信息使用一句文本摘要。这样可以减少后台仪表盘感。

### 7.3 三个分类标签

标签名称：

- 优先机会 1；
- 补充后判断 2；
- 偏好范围外 3。

行为规则：

- 初始只显示“优先机会”；
- 点击“补充后判断”后，优先机会和偏好范围外内容隐藏；
- 点击“偏好范围外”后，只显示对应岗位；
- 每个岗位只能进入一个展示分类；
- 数量为 0 时仍可保留标签并展示清楚的空状态，也可在验证后决定是否隐藏；
- 键盘和屏幕阅读器可以识别当前选中标签。

“待补信息”改为“补充后判断”，因为后者更能表达完成动作后的结果。

### 7.4 优先机会卡片

第一层信息顺序：

1. 真实公告与人工核对状态；
2. 截止紧迫度；
3. 学校或报考单元 + 岗位名称；
4. 省、市、区 + 地图入口；
5. 用工形式、学段学科、招聘人数；
6. 已通过条件数量 + 一个待确认风险；
7. 关键提醒；
8. 官方依据与保存操作。

示例：

```text
真实公告 · 已人工核对                         6 天后截止

杭州某公办初中 · 语文教师
杭州 · 余杭区 · 杭州某公办初中              地图 ↗

事业编 · 初中语文 · 招 2 人

3 项已通过                         户籍待确认
公告未明确是否限制户籍，报名前建议向招聘单位确认。

[查看官方依据]                    [保存机会]
```

### 7.5 地图入口

地点是岗位比较信息，不是详情附属信息。地图入口紧跟地点行显示。

规则：

- 明确学校：`市 + 区 + 学校名称`；
- 只有区县：显示行政区，不虚构学校；
- 录用后选岗：明确写“录用后选岗”；
- 连市区都不明确：不显示地图入口；
- 地图使用用户主动点击的国内网页外链；
- 点击前不加载地图 SDK、不申请当前位置；
- 地图失败不影响岗位信息和官方依据。

本轮不内嵌完整地图。等单一分类稳定出现 8 个以上真实岗位，并且用户明确需要比较通勤或区域分布后，再验证桌面端列表/地图分屏。

### 7.6 按钮系统

“查看官方依据”和“保存机会”统一：

- 高度：44px；
- 圆角：10—12px；
- 字号和图标尺寸一致；
- 同一行时上下边缘对齐；
- 移动端触控面积不小于 44px；
- 两按钮并排时可以等宽。

但视觉层级不同：

- “查看官方依据”：主按钮、实心品牌色；
- “保存机会”：次按钮、描边或浅色背景。

统一大小解决视觉不整齐，保留主次解决用户不知道先做什么的问题。

### 7.7 补充后判断

顶部先说明：

> 这些岗位不是“不符合”，只需要补充或确认一项信息。完成后会自动进入优先机会或不符合。

每张卡只突出一个主动作：

- 补充普通话等级；
- 确认专业目录口径；
- 补充户籍或生源地；
- 查看需要联系招聘单位的问题。

不要在列表卡重复展示全部已通过条件。

点击这个主动作后，不得回到基础画像第 1 屏，也不得让用户重新填写地区、学历和专业。系统应进入当前岗位的“定向补充”界面，并遵守以下规则：

- 只询问导致当前岗位无法判断的字段；
- 顶部保留岗位名称、地点、当前状态与返回结果页入口；
- 解释为什么需要这项信息，以及它还会影响多少个岗位；
- 已经填写的基础信息只做摘要，不重复提问；
- 保存后立即重新判断，并明确显示“补充前 → 补充后”的状态变化；
- 如果判断未变化，返回“补充后判断”并聚焦原岗位；如果判断发生变化，打开岗位移动后的新分类并解释变化；
- 如果用户主动选择“修改全部报考信息”，才进入基础画像编辑流程。

“缺少用户事实”和“公告口径有歧义”必须走两条不同流程：前者进入定向补充，后者进入“建议官方确认”，不能通过填写一段文字自动变成符合。

### 7.8 偏好范围外

顶部说明：

> 这些岗位资格可能符合，但不在你设置的地区或用工偏好内，因此不参与优先排序。

视觉上比优先机会更安静：

- 使用普通列表或弱边框卡片；
- 明确“超出杭州优先范围”“用工形式非优先”等原因；
- 提供“查看”或“调整偏好”；
- 不使用红色和“不符合”文案。

## 8. 桌面端与移动端响应式方案

### 8.1 核心判断

电脑端页面不需要真正铺满 1920px。完全铺满会造成文字行过长、视觉焦点松散、按钮离内容过远。正确目标是：

> 背景和页面舞台铺满，核心内容保持可读宽度，并利用横向空间建立并列关系。

### 8.2 建议断点与内容宽度

| 范围 | 页面行为 | 左右留白 | 内容组织 |
|---|---|---:|---|
| 320—479px | 小屏移动端 | 16px | 单列；按钮整行；标签可横向滚动 |
| 480—767px | 大屏移动端 | 20px | 单列；事实标签可换行 |
| 768—1023px | 平板/窄桌面 | 24—32px | 首页可单列；表单两列；结果卡仍以单列为主 |
| 1024—1439px | 标准桌面 | 32—48px | 12 栏网格；首页左右分栏；结果卡内部双区 |
| ≥1440px | 宽桌面 | 自动居中 | 内容最大 1280px，背景继续铺满 |

不要按具体设备品牌编写布局，而是根据内容是否拥挤决定断点。

### 8.3 首页桌面端

- 内容最大宽度 1280px；
- 左文案 5 栏，右预览 7 栏；
- 页面可以使用全宽浅色或渐变背景形成完整舞台；
- 主标题仍限制行宽，不让一行跨越半个屏幕；
- 预览卡可以随屏幕增加宽度，但不能因此增加字段。

### 8.4 结果页桌面端

结果页建议从当前约 900px 的窄容器扩大到 1180—1280px。

优先机会卡在桌面内部使用两区：

```text
┌────────────────────────────────────────────────────────────┐
│ 真实公告 · 已核对                              6 天后截止 │
├───────────────────────────────┬────────────────────────────┤
│ 杭州某公办初中 · 语文教师      │ 3 项已通过                 │
│ 杭州 · 余杭区 · 学校  地图 ↗   │ 户籍待确认                 │
│ 事业编 · 初中语文 · 招 2 人    │ 关键提醒一句话             │
├───────────────────────────────┴────────────────────────────┤
│ [查看官方依据]                         [保存机会]          │
└────────────────────────────────────────────────────────────┘
```

建议比例：岗位事实 7 栏，资格判断 5 栏。这样利用横向空间，但没有增加信息量。

“补充后判断”的两张卡可以在桌面端形成两列；“偏好范围外”的三条内容可以使用两列或三列紧凑列表。屏幕变窄时自动恢复单列。

### 8.5 为什么暂不做固定右侧边栏

右侧边栏很容易重新塞入覆盖说明、画像摘要、提醒和帮助，导致页面再次拥挤。在真实结果数量较少的当前阶段，优先通过卡片内部横向布局解决宽度问题。

只有当用户稳定同时比较多个岗位时，才考虑“左侧岗位列表 + 右侧选中岗位”的 master-detail 分屏。

### 8.6 移动端结果页

- 顶部标题、核对时间上下排列；
- 分类标签可横向滚动，但当前项必须清楚；
- 结果卡按状态、岗位、地点、事实、判断、按钮顺序堆叠；
- 地点与地图入口尽量在同一行，空间不足时地图入口换行但不隐藏；
- 两个卡片按钮可上下排列并等宽；
- 完整依据使用详情页或底部抽屉，不在卡片内无限展开；
- 不设置固定高度卡片，避免中文换行时被裁切。

## 9. 视觉系统与组件规则

### 9.1 视觉语气

关键词：可信、清楚、克制、轻未来感。

不采用：

- 深色交易终端式大屏；
- 大量霓虹渐变；
- 多层玻璃拟态；
- 每个区块都是悬浮卡片；
- 每一行文字都变成胶囊；
- 只为了“高级感”而使用低对比度灰字。

### 9.2 基础尺寸建议

| 组件 | 桌面端 | 移动端 |
|---|---:|---:|
| 页面标题 | 32—40px | 28—34px |
| 首页主标题 | 52—66px | 38—48px |
| 岗位标题 | 20—22px | 18—20px |
| 正文 | 14—16px | 14—16px |
| 辅助文字 | 12—13px | 12—13px |
| 主按钮高度 | 48px | 48px |
| 卡片操作按钮 | 44px | 44—48px |
| 表单控件 | 46—48px | 48px |
| 卡片圆角 | 14—18px | 12—16px |

### 9.3 颜色语义

- 品牌蓝：主要操作和当前选中状态；
- 绿色：已通过或已核对；
- 琥珀色：待确认、截止临近；
- 红色：只用于明确错误、已截止或明确不符合；
- 中性灰：结构、次要信息和偏好范围外。

重要状态必须同时有文字或图标，不能只依赖颜色。

### 9.4 组件清单

后续开发建议统一以下组件：

- `ResultSummary`：结果总览和核对时间；
- `FilterSummary`：当前条件和修改入口；
- `ResultCategoryTabs`：三类互斥结果；
- `OpportunityCard`：优先机会；
- `PendingDecisionCard`：补充后判断；
- `OutsidePreferenceRow`：偏好范围外；
- `LocationLine`：省市区、学校和地图入口；
- `DecisionSummary`：已通过数量和待确认项；
- `EvidenceButton`：统一的官方依据主操作；
- `EmploymentPreferenceSelector`：三档用工偏好；
- `TrustLine`：官方来源、人工核对和更新时间；
- `NextActionPanel`：保存成功后的单一下一步；
- `OfficialQuestionComposer`：确认原因、公告原文、咨询模板和官方联系方式；
- `OpportunityComparison`：最多三个已保存岗位的关键差异比较；
- `MainTargetSelector`：将岗位设为主要目标或恢复为备选。

访客示例和登录后的真实结果应复用同一个信息骨架，避免出现两套视觉语言。

## 10. 关键状态与边界设计

### 10.1 没有优先机会

不要只显示空白标签页。应说明原因，并把“补充后判断”作为下一步：

> 暂时没有可直接优先的机会；补充 1 项信息后，可以继续判断 2 个岗位。

### 10.2 当前地区未覆盖

必须写“暂未收录”，不能写“当地没有招聘”。同时展示真实覆盖城市、最后核对时间和订阅入口。

### 10.3 已覆盖但当前没有招聘

说明已核对范围与时间，并提供预计下一窗口时，明确标记为参考节奏而非官方日期。

### 10.4 全部明确不符合

展示主要原因、可修改的个人字段和偏好范围外岗位，不用焦虑式文案。

### 10.5 官方来源暂不可访问

岗位信息仍可查看，来源按钮显示“暂时无法打开”，不导致页面失败。

### 10.6 加载与更新

- 首屏先展示页面骨架，不使用大面积旋转动画；
- 筛选切换在 160—220ms 内完成；
- 数据重新判断时说明“正在根据新条件更新”；
- 更新后只强调发生变化的状态，不让整页闪烁。

## 11. 国内网络与可访问性要求

- 不使用 Google Fonts、境外图标 CDN 或运行时 UI CDN；
- 字体使用系统字体或随产品部署；
- 图标随构建产物部署；
- 浏览器只调用同源接口；
- 地图和官方公告均为用户主动点击外链；
- 外链失败不影响核心页面；
- 键盘可以操作分类标签、表单和按钮；
- 触控目标不小于约 44px；
- 中文正文保持清楚对比度；
- 移动端支持 320px 宽度且不横向溢出；
- 不用 hover 承载必要信息。

## 14. 结果之后的三个延伸方向

本轮进一步形成了三个相互连接的下一阶段方向：保存后给出下一步、生成官方咨询问题、多岗位比较。它们不是三个孤立功能，而是把“看到岗位”继续推进到“完成真实报考行动”的连续路径。

当前已用可交互方案稿验证三个关键界面状态：保存后展开下一步、咨询问题复制与个人答复记录、比较后设置主要目标。该方案稿用于验证信息结构和交互理解，不代表生产能力已经完成。

```text
看到岗位
  ↓
保存机会
  ↓
系统给出一个下一步
  ↓
遇到无法直接判断的条件
  ↓
生成官方咨询问题并记录个人答复
  ↓
同时保存多个机会
  ↓
比较关键差异并设置主要目标
  ↓
进入统一日程与报考推进
```

### 14.1 方向一：保存后直接给出下一步

#### 目标

把“保存机会”从普通收藏升级为报考推进的起点。保存后的反馈不只说明操作成功，还必须告诉用户系统同步了什么、现在最应该做什么。

#### 推荐交互

用户点击“保存机会”后，在当前卡片下方或移动端底部抽屉中显示：

```text
已保存，并加入报考日程

报名截止：10 月 18 日
下一步：先确认户籍要求

[查看确认方式]    [稍后处理]
```

桌面端使用紧邻岗位卡的轻量行动面板，不用遮挡整页的大模态框；移动端使用可关闭的底部抽屉。反馈出现后，原按钮改为“已保存”，并保持可撤销。

#### 下一步生成顺序

系统只能给出一个主要下一步，并按照以下优先级选择：

1. 会影响“能不能报”的阻塞条件；
2. 72 小时内到期的报名、缴费、确认等官方节点；
3. 缺失的报名材料或个人信息；
4. 官方已明确但尚未处理的日程；
5. 日期未公布时，开启站内提醒。

| 当前状态 | 保存后的主要行动 |
|---|---|
| 初步符合，无关键风险 | 查看材料清单 |
| 需要补充信息 | 补充对应信息 |
| 建议官方确认 | 查看确认原因并生成问题 |
| 72 小时内截止 | 检查官方报名入口与材料 |
| 时间尚未公布 | 开启站内提醒 |
| 已经报名 | 查看下一官方节点 |

#### 数据与规则要求

- 读取岗位匹配状态、关键未知项、官方时间节点和用户当前推进状态；
- 只同步公告已明确的日期，不推测待通知节点；
- 同一岗位、节点和提醒阶段保持幂等；
- 登录后恢复用户原来的保存动作，不要求重新操作；
- 撤销保存时停止未来提醒，但历史操作按产品既有规则保留。

#### 不做什么

- 不自动标记为“已报名”；
- 不自动设置主要目标；
- 不替用户联系招聘单位；
- 不自动创建推测日期；
- 不把“保存”包装成报名成功。

#### MVP

第一版只实现：保存成功、同步官方截止时间、根据岗位状态给出一个下一步。暂不建设复杂材料管理。

#### 验证指标

- 保存后继续点击下一步的比例；
- 保存后 24 小时内发生有效推进动作的比例；
- 只收藏但 7 日内完全没有推进的比例；
- 用户能否区分“保存成功”和“报名成功”。

### 14.2 方向二：为“建议官方确认”生成咨询问题

#### 目标

把“建议咨询招聘单位”从一句免责声明变成可执行动作，同时保持产品不替招聘单位作最终判断的边界。

#### 状态边界

- “需要补充信息”：公告规则清楚，但用户尚未填写；
- “建议官方确认”：用户信息已填写，但公告规则仍存在解释空间。

只有第二种状态生成咨询问题。

#### 页面结构

桌面端使用左右两区：

```text
左侧：为什么需要确认                 右侧：建议咨询问题
公告规则与系统无法确定的原因           可编辑文本
对应公告原文                           [复制问题]
官方单位、电话、咨询时间               [已联系，记录答复]
```

移动端按照“原因 → 原文 → 问题 → 联系方式 → 记录答复”单列展示。

建议问题示例：

> 您好，我准备报考“初中语文教师”岗位。我的本科专业为“汉语言文学（师范）”，毕业证书上的专业名称为“汉语言文学”。请问该专业是否符合岗位要求的“中国语言文学类”？如需按特定专业目录核对，也请告知目录名称或版本，谢谢。

#### 首批支持类型

1. 专业名称与专业目录；
2. 教师资格取得状态和最迟取得时间；
3. 户籍、生源地、居住证；
4. 应届身份、劳动关系和社保记录。

#### 官方联系方式规则

- 只展示公告或可核验官方页面提供的联系方式；
- 同时展示来源位置与最后核对时间；
- 联系方式缺失时，不从非官方社群拼凑；
- 产品只提供复制和查看，不自动拨号沟通或发送邮件；
- 模板默认不填入身份证号、详细住址等敏感信息。

#### 答复记录

用户联系后可以记录：

- 确认符合；
- 确认不符合；
- 仍不明确；
- 暂未联系。

个人答复只影响该用户的岗位状态，并明确标记为“你的咨询记录”。它不能直接更新所有用户的公共规则；只有获得可核验的补充公告或正式书面依据后，才能进入公共规则与数据版本。

#### 风险控制

- 模板使用询问语气，不预设答案；
- 模板可编辑；
- 明确“请以招聘单位答复为准”；
- 展示岗位名称、问题条件和公告核对时间；
- 不把问题模板显示成官方意见；
- 不因用户个人口头答复提高公共数据置信度。

#### MVP

先覆盖专业目录、教师资格时间、户籍/应届三类问题，只实现确认原因、原文摘要、问题模板、复制、官方联系方式与答复记录。

#### 验证指标

- 模板打开率与复制率；
- 官方联系方式查看率；
- 用户记录答复的比例；
- “建议确认”岗位被继续推进而非直接放弃的比例；
- 用户是否误认为模板或个人答复就是官方公共结论。

### 14.3 方向三：多岗位比较

#### 启动条件

多岗位比较不是当前立即建设的默认功能。只有出现以下行为证据后进入开发：

- 有明显比例的用户同时保存两个以上岗位；
- 用户频繁在多个岗位详情之间来回切换；
- 用户持续提出“这两个先准备哪个”；
- 保存岗位之间真实出现报名、复审或考试时间冲突。

#### 产品目标

帮助用户看清差异、安排准备顺序，不替用户计算“最优岗位”，也不输出难以解释的综合推荐分。

#### 比较范围

桌面端最多三个岗位，移动端首版最多两个岗位。

首版只比较：

- 地点；
- 用工形式；
- 学段与学科；
- 招聘人数；
- 报名截止时间；
- 当前资格状态；
- 关键待确认项；
- 当前下一步；
- 已明确的考试或复审冲突；
- 最后核对时间。

明确不比较：录取概率、竞争激烈度、学校排名、工作强度、领导风格、未经核实的薪资和系统主观“岗位好坏”。

#### 桌面端布局

使用按维度排列的比较矩阵，而不是并排复制三张完整岗位卡：

```text
                 杭州岗位       宁波岗位       嘉兴岗位
地点             杭州余杭       宁波鄞州       嘉兴南湖
用工形式         事业编         备案制         合同制
报名截止         6 天后         12 天后        待通知
资格状态         初步符合       补充后判断     建议确认
关键问题         户籍           普通话         专业目录
下一步           确认户籍       补普通话       复制咨询问题
```

差异项适度强调，不能把整张表涂成多色状态面板。每个岗位只提供“设为主要目标”，其他已保存岗位继续作为备选。

#### 移动端布局

移动端不压缩三列表格。采用两个岗位的纵向摘要卡，或者按单个比较维度依次展示。阅读顺序仍是地点、形式、截止、状态、问题、下一步。

#### 行动冲突

比较页最有价值的能力不是静态字段，而是发现：

- 两个岗位的报名或考试时间冲突；
- 多个岗位都受同一项缺失信息影响；
- 完成一次资料补充可以重新判断多个岗位。

产品提示冲突和共同动作，但不自动替用户放弃岗位。

#### MVP

用户保存第二个岗位后，轻量提示“比较这两个机会”。首版只比较地点、用工形式、截止时间、资格状态、关键问题和下一步，并允许设置一个主要目标。

#### 验证指标

- 保存两个岗位后进入比较的比例；
- 比较后设置主要目标的比例；
- 比较后继续执行下一步的比例；
- 用户是否因为字段过多而退出；
- 实际发生时间冲突的用户数量；
- 用户是否误解为系统正在替自己选择岗位。

### 14.4 三个方向的实施顺序

1. 先做“保存后的下一步”，因为它直接连接 7 日有效目标推进率；
2. 再做“官方咨询问题”，强化可解释判断和不确定性处理的差异化；
3. 最后根据多岗位保存数据决定是否开发比较功能。

### 14.5 其他后续机会

- 在用户再次进入产品时展示“今天最该做什么”；
- 使用“6 天后截止”作为首层，72 小时内才提升警示强度；
- 详情页先解释判断，再展开公告原文和岗位表定位；
- 在官方依据末尾收集“依据看不懂 / 信息可能有误 / 仍需确认”；
- 用户完成第一次匹配后再渐进介绍保存、日程和公告变化；
- 岗位数量增加后再验证“舒适 / 紧凑”两种列表密度；
- 用一句话解释排序因素，不显示难以解释的综合匹配分。

## 17. 技术实施方案：修复“补充信息却回到基础画像”的断裂

### 17.1 问题定级

该问题定为 **P0 主流程功能缺陷**，不是普通的页面体验优化。

原因是它同时破坏了三个产品承诺：

1. 用户只需完成两屏基础画像即可查看结果；
2. 某个岗位缺什么，系统就只补问什么；
3. 已填写的信息会被记住并复用，不要求重复输入。

它通常不会直接造成服务端数据损坏，但会造成明显的任务中断、重复填写和信任流失。对于以“帮用户判断是否能报”为核心价值的产品，这一问题应先于首页视觉细节和高级功能修复。

### 17.2 复现记录

2026-10-13 在公开受邀试用环境 `https://kbzs.al.qich.top` 使用全新无痕会话完成以下路径：

```text
首页
→ 开始资格预筛
→ 填写地区
→ 填写基础资格
→ 进入 /preview
→ 点击“补充信息后判断”
→ 被带到 /onboarding?from=preview
→ 页面从“1 / 2 地区意向”重新开始
```

点击前结果页已经保有地区、学历和专业等信息；点击后页面却首先再次展示省份、城市和地区偏好，没有出现与当前岗位缺失条件对应的定向补充界面。问题可以稳定重现。

现有相关单元测试共 40 项，全部通过。这个结果并不代表流程正确，而是说明当前测试覆盖了页面与分组逻辑，却没有覆盖“结果页行动之后最终到达哪里、是否只询问缺失字段、提交后是否返回原岗位”这一条跨页面闭环。

### 17.3 已确认的根因

#### 根因一：结果卡把“补充信息”建模成了“回到 onboarding”

`src/lib/ia/opportunities-view.ts` 当前把 `need_more_info` 映射为：

```text
kind = onboarding
label = 补充信息后判断
```

这意味着按钮文案表达的是“补充一个缺失条件”，行动类型表达的却是“重新进入基础画像”。产品语义和路由语义从这里已经分裂。

#### 根因二：预览页对该行动进行了统一硬编码跳转

`src/app/preview/page.tsx` 的卡片行动处理器在收到 `onboarding` 后，固定执行：

```text
/onboarding?from=preview
```

跳转没有携带岗位 ID、缺失维度、来源分类或返回位置，因此目标页面不可能知道用户是为了哪个岗位、需要补什么，也无法在完成后回到原卡片。

#### 根因三：onboarding 只有“首次填写”和“整体编辑”，没有“定向补充”模式

`src/app/onboarding/page.tsx` 只通过是否存在 `from` 参数判断用户是不是在编辑。进入编辑后，视图仍从第 1 屏“地区意向”开始；它不会根据岗位缺失条件跳到某个具体字段。

因此仅给 `/onboarding` 增加更多查询参数不能从根本上解决问题。继续让基础画像页面承担岗位补问，会让一个两屏向导逐渐变成难以维护的多模式页面。

#### 根因四：项目已有补充表单，但结果页没有连接过去

`src/components/opportunities/SupplementForm.tsx` 已经可以根据条件维度，只展示出生日期、户籍、社保、工作经历或公告特有问题；`src/app/opportunities/[unitId]/page.tsx` 也已经具备保存后重新拉取并比较判断变化的逻辑。

这说明“按需显示字段”和“保存后重算”不是从零建设。缺口主要在：

- 预览结果页没有进入这个能力；
- 基础字段缺失时仍被送回完整 onboarding；
- 没有统一的来源与返回上下文；
- 访客本地画像和已登录服务端画像的保存通道没有统一。

#### 根因五：已登录受邀用户的补充事实存在持久化风险

当前详情页补充信息写入本机的 `kb_profile_supplement_v61`，而受邀模式下的已登录机会匹配由后端读取服务端画像。如果用户已有服务端画像，本机补充事实不会自动合并进去；现有登录迁移逻辑也会在发现服务端已有画像时直接返回。

因此完整修复不能只把按钮改成跳转详情页。否则访客看起来可以填写，已登录用户却可能保存后没有真正影响服务端判断。

### 17.4 目标流程

修复后的主流程应为：

```text
结果页“补充后判断”分类
        ↓
点击某岗位“补充 1 项继续判断”
        ↓
定向补充页读取当前画像与最新岗位条件
        ↓
只展示仍然缺失、且用户可以回答的字段
        ↓
保存事实到当前有效画像
        ↓
重新计算当前岗位，并刷新受影响的其他岗位
        ↓
显示“补充前 → 补充后”
        ↓
回到结果页的新分类并聚焦该岗位
```

如果补充后仍缺信息，岗位留在“补充后判断”；如果变为初步符合，岗位移动到“优先机会”；如果事实明确不满足要求，岗位移动到“不符合/暂不推荐”区。系统必须解释变化，不能让卡片静默消失。

#### 必须额外处理：真实岗位与虚拟示例不能共用同一种承诺

当前 `/preview` 明确把岗位标为“功能示例 · 不是当前真实岗位”，但卡片又提供“补充信息后判断”这种真实任务式按钮。这会让用户自然地认为自己正在推进一个真实岗位，也正是本次问题让人感到严重的原因之一。

推荐采用明确的双轨：

- **真实岗位结果**：按钮使用“补充 1 项继续判断”，进入真实定向补充，保存事实并重算；
- **虚拟示例**：按钮使用“体验补充后如何变化”，进入非持久化演示，不收集或保存额外敏感事实，结束后仍明确标注“这是示例”；
- 如果 `/preview` 后续改为展示真实、可追溯的公开机会，则可以统一使用真实补充流程，但必须同时移除“虚拟示例”的产品语义。

不能一边把岗位称为虚拟示例，一边让用户为它补充出生日期、户籍或社保信息。修复跳转时应同时修复这条信任边界。

### 17.5 页面与路由设计

#### 基础画像页继续只做两件事

`/onboarding` 只承担：

1. 首次完成基础画像；
2. 用户主动选择“修改全部报考信息”。

它不再承担岗位卡片发起的定向补问。

#### 新增专用定向补充路由

针对真实岗位推荐新增：

```text
/opportunities/[unitId]/supplement?origin=preview&bucket=need_more_info
```

路由使用岗位 ID 作为稳定上下文。`origin` 和 `bucket` 只能接受产品定义的枚举值，不接受任意 `returnUrl`，避免开放重定向和不可控回程。

缺失字段不直接相信 URL 参数。页面加载后必须根据“当前画像 + 当前岗位最新规则”重新计算，得到仍然缺失的字段；这样可以避免旧链接、规则更新或手工修改地址造成错误提问。

推荐同时增加该动态路由的 `loading.tsx`，在较慢的国内网络下立即显示岗位摘要和表单骨架，避免用户点击后误以为没有响应。

如果保留当前虚拟预览，使用单独的 `/preview/supplement/[unitId]` 或结果页内演示面板，并复用同一个展示组件，但把 `mode` 明确设为 `demo`：不调用真实画像保存接口，也不把演示答案迁移到用户画像。

#### 为什么选择独立页面而不是弹窗

首版选择独立页面更稳妥：

- 移动端键盘、日期选择器和省市联动更容易处理；
- 刷新、返回和失败恢复有稳定地址；
- 辅助技术的标题、焦点和错误播报更清楚；
- 可以兼容访客、本地演示和受邀登录三种状态；
- 后续仍可在桌面端用拦截路由呈现为侧滑面板，而不改变业务模型。

### 17.6 定向补充页的信息结构

页面只承担一个问题：“还差什么，补完后结果怎样变化？”

#### 桌面端

使用最大约 1120px 的双栏布局：

```text
┌──────────────────────────────────────────────────┐
│ ← 返回结果        补充 1 项，继续判断这个岗位       │
├─────────────────┬────────────────────────────────┤
│ 当前岗位上下文    │ 为什么需要这项信息                │
│ 岗位 / 地点 / 截止│ [唯一需要填写的控件]              │
│ 当前：补充后判断   │                                │
│ 已通过 4 项        │ 会同时影响另外 2 个岗位           │
│ 待补 1 项          │ [保存并重新判断]  [暂不提供]       │
└─────────────────┴────────────────────────────────┘
```

左栏约 320—360px，只保留上下文；右栏约 560—680px，完成填写。页面不铺满大屏，也不退回窄移动卡片居中。

#### 移动端

按以下顺序单列：

1. 返回结果；
2. 岗位名称、地点和当前状态；
3. “还差 1 项”；
4. 为什么需要；
5. 唯一输入控件；
6. 影响几个岗位；
7. 底部主操作“保存并重新判断”。

键盘弹起时不能遮挡提交按钮；错误信息紧跟字段，不能只用顶部 Toast。

#### 必须展示的文案层级

- 标题：`补充 1 项，继续判断这个岗位`；
- 原因：`该公告限制宁波户籍，目前你的户籍信息尚未填写`；
- 影响：`填写后会重新判断 3 个相关岗位`；
- 隐私：`信息只用于资格匹配，不会发送给招聘单位`；
- 退出：`暂不提供，保持“补充后判断”`。

已填写的基础画像使用一行摘要折叠展示，并提供弱化的“修改全部报考信息”入口。它不能再次变成页面主体。

### 17.7 字段注册表：只问真正缺失的内容

不要在页面里继续堆叠大量 `if dimension === ...`。推荐建立共享“补问字段注册表”，让匹配维度、表单控件、校验和保存字段有一个统一映射。

| 匹配维度 | 实际补问字段 | 控件 | 是否可自动重算 |
|---|---|---|---|
| `age` | 出生日期 | 日期 | 是 |
| `hukou` | 户籍省/市 | 省市联动 | 是 |
| `social_security` | 社保累计月数 | 数字 | 是 |
| `work_experience` | 相关工作月数 | 数字 | 是 |
| `education` | 学历、必要时学位 | 单选 | 是 |
| `major` | 毕业证专业全称 | 文本 | 是或转人工确认 |
| `graduation` | 毕业时间、就业状态 | 月份 + 单选 | 是 |
| `teacher_cert` | 状态、学段、学科、预计取得时间 | 条件组合 | 是 |
| `other` | 对应 requirementId 的事实回答 | 文本/专用控件 | 视规则而定 |

对于一个维度包含多个子字段的情况，只显示仍缺失的子字段。例如已经填写“已取得教师资格证”，但缺少学段，就只询问学段，不重新问证书状态和学科。

`MANUAL_REVIEW` 不进入此注册表。它代表公告本身存在歧义，应进入官方确认流程，而不是把用户的一段回答当成官方资格结论。

### 17.8 状态模型

定向补充页建议使用清楚的有限状态，而不是多个相互独立的布尔变量：

```text
loading
→ ready
→ saving
→ recomputing
→ changed | unchanged
→ returning

任意阶段 → recoverable_error
```

关键业务分支：

| 当前情况 | 页面行为 |
|---|---|
| 有可回答的 UNKNOWN 字段 | 展示定向补充表单 |
| 只有 MANUAL_REVIEW | 转入“建议官方确认”界面 |
| 缺失字段已经被其他页面补齐 | 提示“结果已更新”，返回岗位 |
| 岗位已截止或来源失效 | 不再要求补信息，优先展示闸门状态 |
| 岗位规则版本已更新 | 使用新版本重算，并说明核对时间 |
| 用户暂不提供 | 保持 UNKNOWN，不转换为 FAIL |
| 保存失败 | 保留输入，允许重试，不返回结果页 |

### 17.9 保存与重算策略

#### 访客

访客继续使用现有本机存储，但通过统一画像仓储写入：

- 基础画像写入 `kb_guest_profile_v61`；
- 条件事实写入 `kb_profile_supplement_v61`；
- 保存后重新装配完整画像；
- 重算当前岗位，同时刷新结果页分组；
- 不把用户答案写入分析事件。

现有本地存储键可以继续兼容，因此不要求数据库迁移。

#### 已登录受邀用户

已登录用户不能只写本机 supplement。首版可复用现有 `GET /api/profile` 与 `PUT /api/profile`：

1. 读取服务端完整画像；
2. 只合并用户本次明确提交的字段；
3. 保留其他基础与条件字段；
4. 保存完整画像；
5. 再调用岗位详情/匹配接口重算。

为了降低误覆盖风险，后续可把它收敛为 `PATCH /api/profile`，并加入 `profileRevision` 或 `updatedAt` 乐观锁。首轮试用用户量较小，使用现有 PUT 完成字段级合并即可上线，不需要为了这个缺陷先引入复杂的数据版本系统。

#### 登录迁移

当前“服务端已有画像就完全跳过访客迁移”的策略需要改为字段级合并：

- 服务端已有非空事实默认保留；
- 服务端缺失、访客刚补充的事实补入；
- 如同一字段两端都有不同值，不静默覆盖，登录后提示用户确认；
- 合并完成后再清理或标记本机待迁移事实。

这样用户在访客结果页补过户籍，登录保存岗位后不会丢失这次回答。

### 17.10 返回结果页的规则

返回不能只使用 `/preview`，还需要恢复用户任务上下文。

推荐的受控上下文为：

```text
origin = preview | opportunities | detail
bucket = priority | need_more_info | out_of_preference
focus = unitId
```

保存后的处理：

- 判断未变化：回到 `need_more_info`，聚焦原岗位并提示“仍需补充/确认什么”；
- 变为初步符合：打开 `priority`，聚焦已移动的岗位，并显示“已从补充后判断移入优先机会”；
- 变为明确不符合：进入相应非优先分类，解释是哪条事实导致变化；
- 变为建议官方确认：打开确认分类或详情确认区，不能继续显示成“可再填写”；
- 用户取消：回到原分类和原滚动位置，内容不改变。

结果页应通过 `tab` 与 `focus` 恢复分类和焦点；滚动完成后把焦点移到卡片状态标题，并使用非打断式状态消息播报变化。

### 17.12 技术可行性评估

总体判断：**可行性高，改动规模中等，不需要推翻现有匹配引擎。**

| 能力 | 当前基础 | 还需完成 | 风险 |
|---|---|---|---|
| 缺失维度识别 | 匹配结果已经返回 UNKNOWN/MANUAL_REVIEW | 统一转换为补问意图 | 低 |
| 按维度展示表单 | 已有 SupplementForm | 补齐基础字段并组件化 | 中 |
| 保存后重算 | 详情页已有实现 | 抽为共享流程 | 低 |
| 访客保存 | 已有本机存储 | 统一调用与回程 | 低 |
| 已登录保存 | 已有 profile GET/PUT | 正确合并补充事实 | 中 |
| 结果重新分组 | 匹配与分组已有 | 恢复目标分类和焦点 | 低 |
| 响应式 | 现有组件已有移动适配 | 新增双栏/单列补充页 | 低至中 |
| 数据库 | 画像已经能容纳条件事实 | 首版无需变更结构 | 低 |

不需要新增第三方依赖，不需要修改公告抓取与规则数据管线，也不需要重写资格匹配算法。最大风险不是技术难度，而是继续保留多套保存通道，使访客和登录用户得到不同结果。因此应优先收敛画像读写边界。

### 17.13 分阶段实施

#### P0-A：先修复错误去向

- 将 `need_more_info` 的行动类型从 `onboarding` 改成 `supplement`；
- 新增定向补充路由与岗位上下文；
- 明确虚拟示例走 `supplement_demo`，不保存敏感事实；
- 只展示当前缺失字段；
- 保存后重算并显示状态变化；
- 增加端到端回归测试。

此阶段完成后，用户不再回到地区意向第 1 屏。

#### P0-B：统一访客与登录态保存

- 建立统一画像仓储；
- 访客写本地，受邀已登录写服务端；
- 补齐登录时的字段级迁移；
- 验证跨刷新、跨登录后的结果一致性。

此阶段完成后，“保存成功”才真正代表后续匹配会复用该信息。

#### P1：完善上下文与多岗位影响

- 返回时聚焦原岗位或新分类；
- 显示一次填写影响几个岗位；
- 对已被其他页面补齐、规则更新和岗位截止做专门状态；
- 对基础字段实现子字段级补问。

#### P2：在数据支持下继续优化

- 桌面端把专用页面呈现为结果页侧滑面板；
- 多个岗位缺同一字段时支持“一次补充，批量重算”；
- 根据真实退出率优化字段解释与顺序；
- 若出现画像并发修改，再增加 PATCH 与版本冲突处理。

### 17.14 测试与验收矩阵

#### 必须新增的端到端回归

```text
全新访客
→ 完成两屏基础画像
→ 看到一个“补充后判断”岗位
→ 点击“补充 1 项继续判断”
→ 页面只展示该缺失字段
→ 地区、学历和专业没有被重新询问
→ 提交
→ 当前岗位重新判断
→ 返回正确分类并聚焦当前岗位
```

#### 单元与组件测试

- `need_more_info` 返回 `supplement`，不再返回 `onboarding`；
- 字段注册表对每个维度映射正确；
- 已有子字段不重复展示；
- `MANUAL_REVIEW` 永远不进入可自动判定表单；
- 未填写保持 UNKNOWN，不产生 FAIL；
- 保存失败保留输入；
- 路由参数只接受定义好的 origin/bucket；
- 补充前后状态比较文案正确。

#### 三种身份都要验收

| 场景 | 保存位置 | 刷新后 | 登录后/换设备后 |
|---|---|---|---|
| 未登录访客 | 本机 | 保留 | 登录时迁移 |
| demo 已登录 | 依当前 demo 约定使用本机 | 保留 | 不承诺跨设备 |
| invited 已登录 | 服务端 | 保留 | 跨设备恢复 |

#### 边界测试

- 岗位在填写过程中截止；
- 官方来源失效；
- 规则版本更新后缺失字段发生变化；
- 同一字段影响多个岗位；
- 用户填写 0 个月社保，而不是留空；
- 户籍只选省、岗位要求到市；
- 网络中断、重复提交与返回重试；
- 用户从补充页主动修改全部报考信息；
- 补充后从“待补”变为“明确不符合”；
- 页面刷新与浏览器后退不会清空已输入内容。

### 17.15 埋点与效果判断

建议记录以下不含答案正文的事件：

- `supplement_opened`：岗位、缺失维度数量、来源；
- `supplement_started`：开始编辑的维度类型；
- `supplement_submitted`：提交字段数，不记录值；
- `supplement_recomputed`：前后状态、是否变化；
- `supplement_abandoned`：退出阶段与来源；
- `supplement_returned_to_result`：返回分类与是否成功聚焦。

核心指标不是“表单提交量”，而是：

1. 结果页进入补充流程的比例；
2. 定向补充完成率；
3. 平均重复提问字段数，目标为 0；
4. 补充后成功回到岗位的比例；
5. 补充导致结论变化的比例；
6. 补充流程退出率；
7. 已登录用户刷新或换设备后事实仍生效的比例。

### 17.16 发布与回退

推荐使用小范围开关发布：

1. 先只对受邀试用账号开启定向补充路由；
2. 同时保留详情页原有内联表单，作为短期回退入口；
3. 监测保存失败、重算失败和补充页退出；
4. 确认访客与登录态一致后，再删除结果页回 onboarding 的旧分支；
5. 发布后一周复核“重复填写”和“补充后找不到原岗位”的用户反馈。

回退时只关闭新入口并恢复到岗位详情的补充区，不应恢复到基础画像第 1 屏。即使临时回退，也必须维持“有岗位上下文、只补缺失字段”的底线。

### 17.17 本轮明确不做

- 不把所有条件一次性塞进首次画像；
- 不把官方歧义伪装成用户可回答的字段；
- 不在 URL 中暴露或信任完整用户答案；
- 不记录户籍、出生日期等答案正文到分析事件；
- 不为了修复跳转而重写整个匹配引擎；
- 不在首版引入新的表单库、状态库或地图 SDK；
- 不用“跳到详情页某个锚点”代替完整的回程和持久化设计。

这次修复的判断标准不是“按钮不再跳错页面”，而是用户能在岗位上下文中补完唯一缺失事实，看到判断变化，并无损地回到原来的决策位置。

## 18. 官方公告数据方案：从代码样本走向可信监测闭环

### 18.1 结论先行

当前产品不是“自动抓取了很多官网，但数据库中只有少量材料”，而是以下三种数据路径同时存在但没有接成一条主链：

1. 访客预览使用前端代码中的虚拟演示公告；
2. 机会列表使用后端代码中的滚动演示目录，加 3 条人工维护的真实公告镜像；
3. PostgreSQL 已经有公告提交、提取、审核和发布表，但用户机会匹配没有读取这些已发布数据库版本。

后台的“公告链接”模式目前也没有真正访问官网。页面把 URL 字符串本身作为 `content` 提交，解析器收到的是网址文字，而不是网页正文、附件或岗位表。

因此数据库材料少、用户结果中真实官方岗位少，是当前实现边界的直接结果，不是一次抓取失败或数据库查询条件错误。

### 18.2 当前实际上是怎样工作的

#### 用户端预览

```text
src/lib/seed/v61-opportunities.ts
        ↓
getRollingDemoAnnouncements
        ↓
/preview 虚拟示例
```

这部分用于演示资格判断方式，不是从官网实时读取，也不是数据库真实公告。

#### 已登录机会列表

```text
backend/src/matching/catalog.ts        演示目录
backend/src/matching/real-catalog.ts   人工维护真实镜像
                    ↓
getPublishedAnnouncements()
                    ↓
匹配引擎与 /opportunities
```

`real-catalog.ts` 当前只有 3 条真实公告、4 个语文报考单元，覆盖杭州、宁波和鄞州；全部是 AI 初核待人工复核状态。代码注释同时说明其中 2 条已截止、1 条是报名时间待公布的预告，所以当前真实在报名数量为 0。

这些真实资料的官方 URL、附件定位和摘录直接写在 TypeScript 文件里。更新它们需要修改代码并重新部署，严格来说它们是“人工维护的数据镜像”，不是生产级数据库目录。

#### 后台公告流水线

```text
管理员提交 URL 或粘贴正文
→ 本地文件快照 + 数据库元数据
→ 手动点击开始提取
→ 确定性文本解析器
→ 人工审核
→ PublishedAnnouncementVersion
```

这条链已经有数据库表、权限、状态机、证据锚点、审核记录和不可变版本，但当前存在两个决定性断点：

- URL 模式没有下载官方网页；
- 数据库中的 PublishedAnnouncementVersion 没有被 OpportunitiesService 读取。

所以即使后台成功“发布”一条数据库版本，它也不会自动进入用户的机会列表和资格匹配。

### 18.3 当前官网覆盖范围

当前静态覆盖登记只包含三个栏目：

| 地区 | 官方栏目 | 当前方式 |
|---|---|---|
| 杭州 | 杭州市教育局教师招聘栏目 | 人工巡检、代码登记 |
| 宁波 | 宁波市教育局人才招聘栏目 | 人工巡检、代码登记 |
| 鄞州 | 鄞州区政府教育局事业招聘栏目 | 人工巡检、代码登记 |

浙江其他城市均标为暂未收录，江苏尚未开始正式监测。这个覆盖范围与“小范围受邀验证”一致，但不能让用户误认为系统已经全国抓取后只找到了这些岗位。

### 18.4 当前能力差距

| 环节 | 设计目标 | 当前实现 | 结论 |
|---|---|---|---|
| 来源登记 | 维护官网栏目、访问策略和健康状态 | 有 Source 表，覆盖清单仍主要写在代码中 | 部分完成 |
| 新公告发现 | 定时检查列表页/API/RSS | 没有调度器和栏目发现器 | 未实现 |
| URL 抓取 | 获取真实 HTML、状态码、响应头 | 只提交 URL 字符串 | 未实现 |
| 附件下载 | 保存 PDF、Word、Excel、图片 | 没有二进制上传或附件抓取 | 未实现 |
| 内容解析 | HTML/PDF/Excel/OCR 分层解析 | 只有 HTML/纯文本正则解析 | 初级实现 |
| 人工审核 | 原文与字段对照、留痕发布 | 已有基本后台和数据库状态机 | 基础可用 |
| 原件存储 | 私有对象存储与版本控制 | 服务器本地 `.data/snapshots` | 仅适合小规模 |
| 发布版本 | 不可变版本、证据锚点 | 数据库已实现 | 已实现 |
| 用户端消费 | 匹配只读数据库 published 版本 | 匹配读取代码内置目录 | 未接通 |
| 更新检测 | ETag/Last-Modified/哈希/补充公告关系 | 只有手动提交后的内容哈希 | 未形成闭环 |

### 18.5 产品目标：不是“万能全国爬虫”

不建议一开始建设一个声称可以抓全国所有政府站点的通用爬虫。政府网站在栏目结构、动态加载、附件格式、区县层级和访问策略上差异很大，一个通用选择器很快会变成高漏报、难排查的系统。

推荐采用：

> 官方来源注册表 + 通用安全抓取内核 + 少量站点适配器 + 人工审核

其中：

- 通用内核负责 HTTP、限速、条件请求、重试、快照和哈希；
- 每个官网适配器只负责发现列表、详情和附件；
- 解析器按 HTML、PDF、Excel、扫描件分层；
- 高影响字段必须经过人工审核；
- 数据库已发布版本是用户端唯一真实来源。

这比“用 AI 搜索全国公告”更慢一些，但更符合本产品“有依据”的定位。

### 18.6 目标数据链路

```text
官方来源注册表
        ↓
低频调度 / 管理员立即检查
        ↓
栏目发现器：找新增详情页和附件
        ↓
安全抓取器：HTML / PDF / Excel / 图片
        ↓
原始快照与内容哈希
        ↓
分层解析：确定性解析优先，OCR/AI 仅做候选
        ↓
自动一致性校验
        ↓
人工审核与证据定位
        ↓
数据库不可变 Published 版本
        ↓
目录投影为 RecruitmentAnnouncement / ApplicationUnit
        ↓
资格匹配、日程、提醒、变化通知
```

“抓取成功”不是完成。只有经过审核并成功投影到用户端目录，才算一条公告真正进入产品。

### 18.7 来源注册表

在现有 `Source` 基础上补充以下配置或关联对象：

- 官方主体、地区和来源级别；
- 栏目首页、允许访问的域名与路径；
- 发现方式：API、RSS、sitemap、列表页或人工；
- 列表页适配器类型与选择器版本；
- 详情链接识别规则、分页游标或发布日期游标；
- 附件域名白名单；
- robots.txt 与站点条款核对时间；
- 单主机最小请求间隔、并发上限和允许时段；
- 上次发现、上次成功抓取、连续失败次数；
- 启用、暂停、永久停用状态及原因；
- 运营负责人和人工复核 SLA。

来源应该可以在后台新增、暂停和查看健康度，不应继续依赖修改 `coverage.ts` 才能接入一个城市。

### 18.8 发现与抓取策略

#### 发现优先级

按照稳定性和站点负担从高到低选择：

1. 官方开放 API 或公开数据下载；
2. RSS、sitemap、信息公开目录；
3. 官方栏目列表页；
4. 需要浏览器渲染的公开列表；
5. 管理员手动提交作为兜底。

不会绕过登录、验证码、封禁或其他访问控制。遇到这些状态应暂停来源并转人工，而不是更换 IP 继续请求。

#### 安全抓取要求

- 只允许访问来源注册表中的官方域名；
- 防止 SSRF：拒绝本机、内网、云元数据地址和异常 DNS 解析；
- 限制重定向次数、响应大小、下载时长和 MIME 类型；
- 单主机默认并发为 1，请求间隔加入抖动；
- 识别并遵守 robots.txt、429 与 Retry-After；
- 使用明确的 User-Agent 和联系邮箱；
- 保存 ETag、Last-Modified、最终 URL、状态码与响应头；
- 使用条件请求，304 不创建新版本；
- 内容哈希相同不重复解析；
- 下载附件前再次校验域名、类型与大小。

#### 调度频率

试用阶段不需要分钟级抓取。建议：

- 招聘高峰期：主要栏目每 2—4 小时一次；
- 非高峰期：每天 2—4 次；
- 已发布公告的补充/更正页：报名期适度提高频率；
- 管理员可执行“立即检查”，但仍遵守同一主机频控；
- 连续失败后指数退避并提醒运营人员。

具体频率是运营配置，不写死在抓取代码里。

### 18.9 文档与附件解析

使用“能确定就不调用 AI”的顺序：

| 类型 | 首选处理 | 必须保留的证据位置 |
|---|---|---|
| HTML | 正文抽取 + DOM 定位 | URL、标题、段落或 DOM 路径 |
| PDF 有文字层 | 逐页文本与表格解析 | 页码、文本块坐标 |
| XLS/XLSX/ET | 表格解析 | 文件名、工作表、行列/单元格 |
| DOC/DOCX | 文本与表格结构解析 | 段落、表格、行列 |
| 扫描 PDF/图片 | OCR 或文档结构化识别 | 页码、区域坐标、OCR 置信度 |

AI 只负责把已经解析出的内容映射成字段候选和通俗摘要，必须返回证据位置、置信度与不确定原因。它不能绕过审核直接发布截止时间、专业、学历、户籍、人数等高影响字段。

### 18.10 数据模型与目录投影

现有 `Source`、`SourceSnapshot`、`ExtractionRun`、`EvidenceAnchor`、`ReviewRecord` 和 `PublishedAnnouncementVersion` 可以继续使用。建议新增或明确以下对象：

- `CrawlRun`：一次来源检查，记录游标、发现数、状态与错误；
- `DiscoveredDocument`：列表页发现的详情或附件，保存规范化 URL 与首次/最后发现时间；
- `AttachmentSnapshot`：二进制附件的哈希、MIME、大小、存储位置；
- `ParsedDocument`：确定性解析产物及解析器版本；
- `ApplicationUnitVersion`：真正供匹配使用的报考单元结构；
- `PublicationProjection`：把审核后的字段转换成匹配领域对象，并记录失败原因。

当前数据库发布的 payload 是通用候选字段，而匹配引擎需要完整的 `RecruitmentAnnouncement`、版本、单元和 Requirement。中间必须有严格校验的“目录投影”步骤，不能把任意 JSON 直接交给匹配引擎。

目录投影失败时，该版本保持“已审核但不可用于匹配”或进入专门失败状态，后台明确指出缺少的字段，不允许部分错误数据静默进入用户端。

### 18.11 接通数据库与机会匹配

推荐新增 `PublishedCatalogRepository`，职责是：

1. 读取数据库中 `status=published` 的当前版本；
2. 校验版本 payload 的领域结构；
3. 生成匹配引擎需要的公告和报考单元；
4. 排除 withdrawn、失效来源和投影失败版本；
5. 返回目录版本号、最近发布时间和覆盖统计。

`OpportunitiesService` 不再直接导入 `REAL_ANNOUNCEMENTS`。环境规则建议为：

- production / invited：只读取数据库真实 published 目录；
- demo：可以读取演示目录，但每条数据明确标记为 demo；
- test：使用显式测试 fixture；
- 数据库暂时不可用：展示数据源不可用状态，不回退成看起来真实的演示岗位。

已有 3 条 `real-catalog.ts` 真实镜像应通过一次性迁移工具导入流水线、补齐人工复核后发布。导入完成后，代码版本只保留测试 fixture，不再作为生产数据源。

### 18.12 审核后台改进

管理员后台应从“提交与看任务”升级为来源运营工作台：

- 来源健康：正常、失败、暂停、待配置；
- 新发现公告与重复公告；
- 原网页/附件与字段并排；
- 附件工作表、页码和原文高亮；
- 高影响字段缺证据拦截；
- 原公告与补充/延期/更正公告关联；
- 新旧版本差异；
- 即将截止但尚未完成审核的高优先队列；
- 发布后用户端是否成功生成机会的结果；
- 抓取失败、解析失败、投影失败分开统计。

管理员必须能回答：“这条公告现在为什么还没有出现在用户机会页？”

### 18.13 分阶段实施

#### 数据 P0：先把现有链路真正接通

- 修复后台 URL 模式，让后端实际获取白名单官网 HTML；
- 保存真实状态码、响应头、最终 URL 和内容哈希；
- 把 3 条现有真实镜像导入数据库并完成审核；
- 建立数据库 published 版本到匹配领域对象的投影；
- `OpportunitiesService` 改为读取数据库真实目录；
- 增加“后台发布后无需重新部署即可出现在机会页”的端到端测试。

完成这一阶段后，产品才拥有最小的真实数据闭环。

#### 数据 P1：三来源半自动监测

- 为杭州、宁波、鄞州实现栏目发现适配器；
- 增加低频调度、条件请求、哈希去重和失败退避；
- 接入 HTML、PDF、XLS/XLSX/ET 的确定性解析；
- 下载并归档附件；
- 建立来源健康和待审核队列；
- 发布新版本后重算已关注岗位与日程。

这一阶段目标是“3 个来源稳定闭环”，不是立刻扩到全国。

#### 数据 P2：按用户地区扩展到 10—20 个来源

- 根据受邀用户地区意向决定城市顺序；
- 每接一个城市先建立来源台账与黄金样本；
- 对扫描件接 OCR；
- 对复杂专业目录和多附件公告增加 AI 候选提取；
- 建立漏报反馈和每周来源质量复盘；
- 达到稳定 SLA 后再扩下一批来源。

#### 数据 P3：规模化运营

- 对象存储、队列 Worker 与来源分片；
- 补充公告自动关联候选；
- 双人复核高风险变更；
- 数据质量看板和来源级 SLA；
- 经过法律、合规和站点政策复核后逐步扩大覆盖。

### 18.14 验收标准

#### URL 获取

- [ ] 提交官方链接后，快照内容是网页正文而不是 URL 字符串；
- [ ] 非白名单域名、内网地址、超大响应和异常 MIME 被拒绝；
- [ ] 301/302 最终地址、HTTP 状态、ETag、Last-Modified 被保存；
- [ ] 同内容重复抓取不产生重复版本；
- [ ] 429 会遵守 Retry-After，不立即重试；
- [ ] 验证码、登录或封禁出现时来源暂停并转人工。

#### 解析与审核

- [ ] HTML 正文、PDF 页码和 Excel 单元格可以回到原文证据；
- [ ] 高影响字段缺证据不能发布；
- [ ] AI/OCR 结果始终先进入待审核；
- [ ] 修改后通过会记录修改前后内容和原因；
- [ ] 补充、延期和取消公告与原公告建立版本或关系指针。

#### 用户端闭环

- [ ] 数据库发布一条完整公告后，无需修改代码或重新部署即可出现在机会页；
- [ ] 机会页只读取真实 published 版本，演示数据不会混入；
- [ ] 公告撤回、来源失效或投影失败后不会继续作为正常机会；
- [ ] 新版本变化会重新计算匹配、日程和受影响用户；
- [ ] 用户能看到官方来源、证据位置、核对状态和最后更新时间；
- [ ] 未覆盖地区显示“暂未收录”，不显示“没有招聘”。

### 18.15 数据质量指标

不要只看数据库记录数量。建议用以下指标判断系统是否变好：

- 来源覆盖数与来源健康率；
- 最近一次成功检查距当前的时间；
- 新公告从官网发布到被发现的中位时长；
- 抓取成功率、解析成功率、投影成功率；
- 待审核数量和审核中位时长；
- 高影响字段证据完整率，目标 100%；
- 重复公告率与版本关联正确率；
- 用户反馈的漏报、错报和过期记录数量；
- 当前真实在报机会数；
- 数据库发布后成功进入用户端的比例，目标 100%。

### 18.16 技术可行性与工作量判断

| 范围 | 可行性 | 相对工作量 | 主要难点 |
|---|---|---|---|
| 接通现有 3 个来源 | 高 | 中 | URL 安全抓取、目录投影、数据库消费 |
| 扩到 10—20 个来源 | 高 | 中高 | 站点适配、附件格式、审核运营 |
| 覆盖一个省的主要城市 | 可行 | 高 | 区县来源数量、漏报监测、持续运营 |
| 一次性全国自动覆盖 | 技术上可分期实现 | 极高且不建议当前承诺 | 站点差异、合规、人工复核与长期维护 |

现有技术栈能够支持首批来源，不需要先更换 Next.js、NestJS、Prisma 或 PostgreSQL。真正需要补的是抓取 Worker、文档解析、目录投影与来源运营能力。

### 18.17 本轮明确不做

- 不通过搜索引擎结果页代替官方来源注册表；
- 不抓取培训机构、自媒体或聚合站作为资格事实源；
- 不绕过验证码、登录、封禁或反爬措施；
- 不让 AI 自动发布高影响字段；
- 不把 PDF/Excel 内容扁平化后丢失页码和单元格位置；
- 不把演示数据与真实数据库目录混在同一结果中；
- 不把“数据库记录更多”当作比“证据完整、更新及时、用户端可消费”更重要的指标。

官方公告能力的完成标准不是“能粘贴一个链接”，而是一个新公告可以被安全发现、完整留档、可追溯解析、人工核验、数据库发布，并在不重新部署代码的情况下进入用户的资格判断与后续提醒。

### 18.18 主动抓取、官网适配与附件解析技术落地

本节的详细技术设计、技术选型、Module 边界、数据模型、后台任务、文件安全、测试策略与分阶段实施，已整理为独立文档：

- [教招有据：主动抓取、官网适配与附件解析技术方案](./教招有据-主动抓取与附件解析技术方案-2026-10-13.md)

当前版本的核心决策是：

- 用 `@nestjs/schedule` 负责定时投递，用 BullMQ + Redis + 独立 Worker 执行抓取和解析；
- 普通官网默认使用 Node.js `fetch` + Cheerio，只有确实依赖 JavaScript 的来源才回退到 Playwright；
- 为杭州、宁波、鄞州分别建立官网适配器，适配器只描述页面结构，不自行请求网络或抽取资格字段；
- 用 `pdfjs-dist`、SheetJS、Mammoth 和按需 OCR 构成附件解析层，统一输出带页码、工作表和单元格位置的标准文档；
- 开发环境保留本地快照，生产使用开启版本控制的私有 OSS；
- 发布后的数据库版本必须通过目录投影进入机会匹配，静态代码目录不再作为生产事实源；
- 首版不同时引入 Crawlee，等来源数量和链接发现复杂度明显增加后再评估替换网页发现子系统。
