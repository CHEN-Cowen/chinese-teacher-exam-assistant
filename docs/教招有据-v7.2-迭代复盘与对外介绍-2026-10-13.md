# 教招有据 v7.2 迭代复盘：从“展示功能”到“可信决策闭环”

> 文档性质：设计与技术方案复盘
> 日期：2026-10-13
> 当前状态：方案已收敛，代码尚未实现
> 对外口径：所有效果均为设计目标或预期效果，不能表述为已经取得的线上结果

## 1. 一句话介绍这次迭代

这次迭代没有停留在重新画页面，而是同时重构了用户做决定的顺序和官方公告进入产品的方式：用户先看到值得关注的岗位，只在必要时补一项信息，每个结论都能回到官方依据；后台发布真实公告后，不需要重新改代码，机会就能进入匹配。

## 2. 项目背景

“教招有据”希望解决的是一个高风险决策问题：教师招聘公告分散、格式复杂，用户很难快速判断自己能不能报，也很难确认判断依据是否可靠。

原来的产品已经具备画像、匹配、岗位详情、官方依据、保存和日程等能力，但实际体验中出现了两个落差：

1. 功能不少，用户却需要自己从大量信息中找答案；
2. 页面强调真实和可核对，数据链路却仍然依赖少量代码样本。

这意味着问题不只是视觉问题。界面、流程、数据来源和审核机制必须作为一个整体迭代。

## 3. 我们发现了什么问题

### 3.1 首页像一份说明书

首页同时展示产品介绍、长示例、判断依据、待确认事项和免责声明。用户还没有产生兴趣，就需要理解一个完整岗位详情。

问题不是内容错误，而是出现顺序错误：首页应该先回答“它能帮我得到什么结果”和“我现在点哪里”。

### 3.2 填完以后又被再次提问

用户填写基础信息后，又在结果出现前被问想看哪类用工形式。这种分段收集会让用户觉得“为什么还不能看到答案”。

用工偏好虽然不改变资格判断，却会改变结果筛选和排序，因此应该在生成结果前一次收齐。

### 3.3 三类结果没有真正分开

优先机会、需要补充和偏好范围外同时出现在页面里，标签更像统计数字，而不是内容控制器。用户仍需要自己分辨哪些是核心结果。

### 3.4 岗位卡信息等权

岗位、地点、截止时间、资格状态、官方来源和全部条件使用接近的字体和视觉重量。信息齐全，但决策重点不突出。

### 3.5 地图能力被藏得太深

地点会直接影响是否值得报考，但地图入口需要进入详情或展开后才能找到。这让一个高频决策信息变成了附属功能。

### 3.6 桌面端像放大的移动页

移动端的窄单列本身合理，但直接放到 1440px 以上屏幕时，内容被大量空白包围，没有利用横向空间建立对比和层级。

### 3.7 “补充信息”其实是“重新填写”

试用中最严重的流程问题是：用户点击某个岗位的“补充信息后判断”，系统却把他送回基础画像，重新询问地区、学历和专业。

这不只是跳转错误，而是模型错误。产品文案说的是“只差一项”，内部却把它当成“重新编辑整份画像”。

### 3.8 官方材料并没有真正进入用户结果

进一步检查发现，真实材料不足不是因为数据库筛选太严格，而是数据链路没有闭环：后台 URL 尚未稳定获取官网正文，机会列表主要读取代码目录，数据库发布结果没有成为匹配事实源。

## 4. 我们使用了什么方法

### 4.1 先定义每个页面的唯一任务

我们没有先换颜色，而是先问每个页面究竟要帮助用户完成什么：

- 首页：理解价值并开始；
- 填写页：收集影响结果的信息；
- 结果页：回答哪些岗位值得先看；
- 补充页：只解决一个缺失事实；
- 详情页：证明判断；
- 日程页：继续推进报考。

这个方法帮助我们删除了许多“内容本身没错，但放错页面”的信息。

### 4.2 用结果先行重排信息

首页曾比较三个方向：

1. 结果先行；
2. 直接开始；
3. 依据先行。

最终选择结果先行。直接开始路径最短，但首次用户不知道会得到什么；依据先行能建立信任，但首屏阅读负担仍然较高。结果先行在吸引力、清楚程度和可信度之间更平衡。

[查看首页方向原型](./prototypes/教招有据-v7.2-首页方向原型.html)

### 4.3 用状态建模替代颜色分类

我们把“优先机会、补充后判断、偏好范围外”定义成互斥状态，而不是三个颜色不同的标签。点击某个标签时，下方数据集必须真正变化。

同时把事实分成五类：官方事实、系统判断、用户事实、用户偏好和未知状态。这样可以避免把偏好范围外写成不符合，也避免把未知写成失败。

### 4.4 用任务连续性检查跨页流程

针对补充信息 Bug，我们没有只改链接，而是沿着完整任务检查：

```text
从哪个岗位进入
→ 为什么需要补
→ 只问哪个字段
→ 保存在哪里
→ 怎样重新判断
→ 回到哪个分类
→ 用户如何看见变化
```

这使修复从“跳到另一个页面”升级为完整的定向补问闭环。

### 4.5 用可信数据供应链支撑界面承诺

我们把官方公告处理拆成：

```text
来源登记
→ 主动发现
→ 安全获取
→ 原件快照
→ 文档解析
→ 候选字段与证据
→ 人工审核
→ 不可变版本发布
→ 机会匹配
```

这让“真实公告、逐条可核对”不再只是界面文案，而是能够被技术链路证明的产品能力。

### 4.6 用分阶段完成门控制范围

这次迭代同时涉及 UI、画像、匹配、抓取、附件解析和部署。如果全部并行，很容易得到多个半成品。因此我们把 v7.2 拆成：

- v7.2.0：决策体验、定向补充、数据库目录和一个来源闭环；
- v7.2.1：三个来源、Worker、PDF/Excel/ET、OSS 和来源健康；
- v7.2.2：保存后下一步、官方咨询、DOCX/OCR 和来源扩展。

每个阶段必须先完成端到端验收，才进入下一阶段。

## 5. 这次具体怎样迭代

### 5.1 首页：从介绍产品到预演结果

改版前：首页展示较完整的示例和解释。

改版后：首页只保留一个问题、一个主按钮和一条极简结果预览：三类数量、一条岗位、地点、截止紧迫度和资格摘要。

为什么：用户不需要先学会使用产品，应该先看见产品能给出的答案。

预期效果：缩短首次理解时间，提高开始预筛的确定感。

### 5.2 填写流程：一次收齐影响筛选的信息

改版前：基础画像完成后再次询问用工形式。

改版后：第一屏收地区，第二屏收基础资格和三档用工偏好；生成结果前完成。

为什么：填写和回答不能交叉出现。偏好只影响筛选与排序，因此用清楚文案与资格条件分开。

预期效果：减少“我是不是还没填完”的不确定感。

### 5.3 结果页：从信息列表到决策工作台

改版前：多类岗位与解释同时展开。

改版后：

- 顶部直接写“1 个优先机会，2 个补充后可判断”；
- 三个标签切换真正的数据集；
- 岗位卡第一层只突出岗位、地点、截止、用工形式、资格摘要和一个风险；
- 详细规则进入官方依据；
- 地图紧跟地点；
- 两个按钮几何一致，但主次不同。

[查看结果与补充流程原型](./prototypes/教招有据-v7.2-结果与补充流程原型.html)

为什么：用户需要的不是更多字段，而是更快形成“先看哪个”的判断。

预期效果：减少扫读时间，降低把偏好和资格混为一谈的概率。

### 5.4 响应式：桌面利用空间，移动保护顺序

桌面端使用全宽视觉舞台和最大 1280px 内容容器。首页左右分栏，岗位卡内部按“事实 / 判断”双区组织。

移动端恢复单列：状态 → 岗位 → 地点 → 事实 → 判断 → 操作。不是把桌面端等比例缩小。

为什么：可读宽度和空间利用不是同一件事。背景可以铺满，正文不应该无限变长。

预期效果：电脑端不再显得空，移动端仍然能快速完成任务。

### 5.5 定向补充：从重填画像到只补缺失项

改版前：结果页行动被硬编码为返回 onboarding。

改版后：真实岗位进入稳定路由 `/opportunities/[unitId]/supplement`。系统根据最新岗位和当前画像重新计算缺失字段，只渲染仍缺少的子字段。

保存后：

1. 字段级更新画像；
2. 重新获取岗位详情与匹配；
3. 对比补充前后状态；
4. 返回对应标签；
5. 聚焦原岗位并解释为什么移动。

公告歧义进入官方确认，不能让用户填写一段回答后自动变成符合。

为什么：用户应该感受到系统记得已经知道的事实，也知道为什么还要问这一项。

预期效果：重复提问为零，降低补充流程退出，增强判断可信度。

### 5.6 保存：从收藏状态到一个下一步

改版前：保存成功后任务结束。

改版后：保存后只展示一个最高优先级动作，例如确认户籍、处理即将截止节点、准备缺失材料或等待官方通知。

[查看结果后行动原型](./prototypes/教招有据-v7.2-结果后行动原型.html)

为什么：教师招聘有截止时间，普通收藏没有推动真实报考。

预期效果：提高保存后 24 小时内的有效推进动作，同时避免把保存误解成已经报名。

### 5.7 官方确认：把“不确定”变成可执行问题

改版前：只告诉用户“建议咨询招聘单位”。

改版后：展示为什么无法可靠判断、对应公告原文、可编辑问题模板和官方联系方式。用户可以记录个人答复，但答复不成为公共规则。

为什么：可靠产品不应该假装回答所有问题，但应该帮助用户把问题问清楚。

预期效果：减少因不知道怎么问而直接放弃的岗位。

### 5.8 官方公告：从代码样本到数据库事实源

改版前：后台已有流水线骨架，但用户端主要读取静态目录；URL 未形成稳定真实快照。

改版后：

- NestJS 定时器投递任务；
- BullMQ、Redis 和独立 Worker 执行；
- 官网 Adapter 只处理页面差异；
- Node.js fetch 负责安全下载；
- Cheerio、PDF.js、SheetJS、Mammoth 和按需 OCR 处理不同格式；
- 原件进入 OSS；
- 候选字段人工审核；
- 已发布数据库版本通过 `PublishedCatalogRepository` 进入匹配。

为什么：抓取数量不是价值。只有能追溯、能审核、能进入用户结果的数据才是产品数据。

预期效果：公告更新不再依赖修改代码，用户端真实机会能够持续增加，同时保持证据和版本链。

## 6. 技术链路如何支撑产品体验

### 6.1 用户画像为什么不会再丢

统一 `ProfileRepository`，提供两个 Adapter：访客写本机，受邀用户写服务端。服务端增加字段级 PATCH 和乐观锁，定向补充不再用客户端读—改—全量覆盖。

登录时按字段迁移，冲突需要用户确认，因此访客补过的户籍不会因为登录而静默消失。

### 6.2 官网变化为什么不会拖垮整个系统

每个官网只有一个 Adapter 描述列表、正文和附件位置。网络安全、限速、重试和快照全部由抓取执行 Module 统一处理。

官网改版时，变化集中在对应 Adapter；页面结构找不到时必须告警，不能静默变成“今天没有公告”。

### 6.3 PDF 和表格为什么仍能回到原文

附件不会被简单压成纯文本：

- PDF 保留页码；
- Excel 和 ET 保留工作表、行、列；
- DOCX 保留段落和表格单元格；
- OCR 保留页码、坐标和置信度。

因此资格字段可以建立到具体原文位置的证据锚点。

### 6.4 为什么发布后不需要重新部署

机会匹配不再读取生产静态目录，而是通过 `PublishedCatalogRepository` 读取数据库中状态为 published 的版本。静态目录只保留给演示和测试。

管理员审核发布后，目录投影任务校验数据、刷新匹配消费和同步关注日程。代码和事实因此分开。

## 7. 关键取舍

### 7.1 没有做全国万能爬虫

先把三个来源做成稳定闭环，再根据受邀用户地区扩展。这样能看见真实维护成本，也能避免“覆盖很多但无法核验”。

### 7.2 没有默认使用浏览器抓取

普通政府网站优先使用 HTTP + Cheerio。只有确实依赖 JavaScript 的页面才使用 Playwright，降低内存、镜像和故障成本。

### 7.3 没有同时引入 Crawlee

当前 BullMQ 已经承担抓取、解析和投影任务。此时再引入 Crawlee 会形成两套队列。等来源规模和链接发现复杂度增加后再评估。

### 7.4 没有让 AI 自动发布

AI 可以辅助理解复杂资格文字，但不能代替原文、证据和人工审核。学历、专业、年龄、教资和报名时间等高影响字段必须有证据。

### 7.5 没有立即上线多岗位比较

多岗位比较原型已经完成，但只有用户经常同时保存多个真实机会时才有价值。本轮保留原型和埋点，不为了完整感提前开发空功能。

### 7.6 没有依赖动效制造前卫感

产品的前卫感来自清晰结构、快速反馈、可信证据和桌面/移动适配，不来自持续发光、漂浮或复杂数据大屏。

## 9. 怎样验证效果

### 9.1 理解效率

- 10 秒内能否说清产品作用；
- 能否无提示找到开始入口；
- 能否在 10 秒内指出一个优先岗位和原因；
- 能否区分补充后判断、官方确认和偏好范围外。

### 9.2 流程连续性

- 定向补充完成率；
- 已知字段重复提问数，目标为 0；
- 补充后返回原岗位的比例；
- 补充流程退出率；
- 登录、刷新或换设备后事实是否仍生效。

### 9.3 报考推进

- 保存后 24 小时内完成有效动作的比例；
- 官方咨询模板打开、复制和答复记录；
- 日程和材料状态的推进；
- 用户是否误把保存当作已报名。

### 9.4 数据质量

- 来源健康率；
- 官网发布到被发现的时间；
- 抓取、解析、审核和投影成功率；
- 高影响字段证据覆盖率；
- 重复公告、漏报和过期记录；
- 发布后进入用户端的比例，目标为 100%。

## 10. 本次迭代日志

| 阶段 | 观察 | 决策 | 原因 |
|---|---|---|---|
| 首页评审 | 示例过长，与主入口争夺注意力 | 选择结果先行 | 先展示结果形状，再展开依据 |
| 填写评审 | 用工偏好在结果前再次出现 | 移到第二屏 | 生成结果前一次收齐 |
| 结果评审 | 三类内容没有真正分离 | 改成互斥标签 | 状态必须改变内容，不只改变颜色 |
| 卡片评审 | 重点不突出、地图隐藏 | 重排信息层级，地图前置 | 先支持决策，再支持阅读全部字段 |
| 视觉评审 | 两按钮高度形态不同 | 几何统一，主次保留 | 一致不等于同权 |
| 响应式评审 | 桌面端过窄 | 全宽舞台 + 1280px 容器 | 利用空间但控制行宽 |
| 后续探索 | 收藏没有推动行动 | 保存后只给一个下一步 | 从浏览连接到推进 |
| 真实试用 | 补充信息回到 onboarding | 建立定向补充路由与字段注册表 | 修复任务模型，不只修链接 |
| 数据审查 | 官网资料少、数据库与机会页断开 | 建立可信公告供应链 | 数据必须可追溯并被用户端消费 |
| 技术收敛 | 抓取、解析可能阻塞 API | BullMQ + Redis + 独立 Worker | 稳定执行、限速、重试、可恢复 |
| 范围控制 | 多岗位比较看起来完整但需求未证实 | 保留原型，暂不上线 | 用行为数据决定是否投资 |

## 11. 一分钟对外介绍稿

> 这次我没有把“教招有据”只当成一个页面美化项目，而是重新梳理了用户从理解产品、填写条件、查看机会，到补充信息和继续报考的整条路径。
>
> 首页从长篇示例改成结果先行，只保留一个主入口和一条极简岗位预览。用工偏好被放回填写流程，结果页拆成三个真正互斥的分类，地点、地图、截止时间和资格风险被提升到第一层。用户点击补充信息时，也不会再重新填地区和学历，而是在岗位上下文中只补缺失的一项，系统立即重新判断并带他回到岗位的新分类。
>
> 同时，我把数据可信度纳入了同一次迭代。官方公告不再只写在代码里，而是经过来源登记、安全抓取、附件解析、人工审核和数据库发布，再进入资格匹配。这样界面上的“真实公告、逐条可核对”不只是文案，而是有完整技术链路支撑。
>
> 这次迭代的目标不是让页面看起来信息更多，而是让用户更快回答四个问题：哪个岗位值得看、为什么、在哪里、下一步做什么。

## 12. 三分钟介绍结构

1. 教师招聘是高风险、强证据的决策场景；
2. 原产品功能齐全，但首页和结果页把信息平铺给用户；
3. 通过页面任务法重新划分首页、填写、结果、详情和日程；
4. 比较三种首页方向，最终选择结果先行；
5. 把用工偏好放回填写，结果只负责回答；
6. 用互斥状态重做结果分类；
7. 重排岗位卡，把地图、截止和风险前置；
8. 把桌面端从窄单列改成有上限的横向舞台；
9. 通过真实试用发现补充信息流程断裂；
10. 用稳定岗位路由、字段注册表、字段级画像更新和状态回程修复；
11. 把保存扩展为一个下一步，把公告歧义转成官方咨询问题；
12. 检查数据后发现数据库发布和用户端仍未闭环；
13. 建立 Worker、官网 Adapter、附件解析、人工审核和数据库目录；
14. 用分阶段完成门控制范围，暂缓没有行为证据的多岗位比较；
15. 用理解效率、流程连续性、报考推进和数据质量四类指标验证。

## 13. 作品集式总结

### 问题

产品拥有丰富能力，但用户需要自己组织信息；界面承诺可信，真实数据供应却没有完全闭环。

### 方法

页面任务定义、结果先行、状态建模、跨页任务检查、原型比较、可信数据供应链和分阶段交付。

### 关键产出

- 首页、填写、结果、补充和结果后行动原型；
- 桌面与移动响应式规则；
- 定向补充的路由、画像与状态模型；
- 主动抓取、官网 Adapter、附件解析和审核发布架构；
- 完整 v7.2 PRD、验收矩阵、发布与回退方案。

### 预期价值

降低首次理解和结果扫读成本，减少重复填写，把系统的不确定性转化为用户可执行的下一步，并让真实官方公告可以持续进入产品。

### 保持的边界

不承诺全国覆盖，不用综合分制造确定感，不让 AI 自动发布，不把个人咨询变成公共事实，不在需求未被证明时开发多岗位比较。

## 14. 复盘结论

这次迭代最重要的变化，是产品从“展示自己有哪些能力”转向“按照用户做决定的顺序提供能力”：

> 先让我看见机会，再告诉我为什么；缺信息时只问这一项；无法确定时帮我问清楚；保存以后告诉我下一步；所有公共结论都回到官方原文。

界面改版和数据闭环因此不是两个项目，而是同一个可信产品承诺的前后两面。
