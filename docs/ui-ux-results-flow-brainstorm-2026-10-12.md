# 教招有据：首次预筛与结果页 UI/UX 重构发散稿

日期：2026-10-12  
状态：讨论稿，不代表已确认需求，不包含代码修改

## 一句话结论

当前页面的问题不是功能不足，而是“用户想马上看到答案时，页面仍在继续解释和提问”。建议把产品从“表单 + 说明页 + 多层卡片”重构为“轻量画像 + 决策结果工作台”：填写阶段收完必要条件和用工偏好，结果阶段只负责回答“哪些值得看、为什么、在哪里、什么时候截止、下一步做什么”。

## 1. 当前体验诊断

### 1.1 用工形式出现在结果页，打断了用户获得答案的时刻

v7.1 原本为了降低首次填写负担，把用工形式移出了基础画像；当前实现又把“想看哪类用工形式的岗位？”放在预览结果的前面。于是用户完成两屏填写后，没有先看到结论，而是被要求做第二轮选择。

这不是字号或卡片样式问题，而是流程位置不对。最新用户反馈应覆盖旧决策：把用工形式放回第二屏底部，用三档紧凑选择呈现，并允许暂不选择。

推荐文案：

- 只看事业编
- 事业编优先，也看其他官方岗位
- 暂不确定，先全部看看

未选择时按“全部看看”展示，但界面不要伪装成用户已经主动选择。

### 1.2 地图能力存在，但被藏在展开区或详情页

当前访客卡片只有展开“判断依据”后才显示地图入口，登录态列表卡也没有直接地图入口。地点本来就是岗位比较的重要信息，所以用户在第一轮浏览时就应该看到：

> 杭州 · 余杭区 · 杭州某中学　`地图 ↗`

地图入口应放在岗位名称下方的地点行，而不是藏在详情里。现阶段不建议默认嵌入完整地图：当前真实岗位数量少，整块地图会抢占空间、放大“覆盖很广”的错觉，也与国内网络和轻量外链基线冲突。先把地点与地图入口提升为首层信息；当单页稳定出现 8 个以上真实岗位、用户确实需要比较通勤时，再测试桌面端“列表 / 地图”切换或分屏模式。

### 1.3 结果页没有在第一屏回答四个核心问题

用户真正需要在 10 秒内回答：

1. 我有几个值得看的机会？
2. 哪一个最优先？
3. 为什么判断我可能符合？
4. 地点和截止时间是什么？

当前页面先后出现真实监测 Hero、覆盖说明、用工偏好、功能示例说明、结论卡、岗位卡、画像摘要、试用承接和折叠内容。每块单独看都合理，但组合起来让“结论”被很多前置信息包围。

### 1.4 岗位卡的信息虽然齐全，但视觉权重接近

省市区、岗位名、学段、学科、用工形式、人数、学校、截止时间和判断原因都以相近字号和灰度连续排列。结果是“信息都有，但用户需要自己找重点”。重点突出不应只靠把岗位名加粗，而应通过分组、字号、色彩和空间建立层级。

### 1.5 “真实监测”和“虚构示例”混在一条阅读流里

这会同时增加两种成本：用户要反复确认数据真假，产品又不得不重复免责声明。应该先在页面级别建立清楚的事实边界，再让卡片只保留一个轻量标签。

## 2. 推荐的产品结构

```text
首页
  ↓ 一个主入口
基础画像（2 屏）
  1. 地区意向
  2. 资格条件 + 用工偏好（可跳过）
  ↓
结果工作台
  结果摘要 → 筛选摘要 → 状态分组 → 岗位卡片
  ↓
岗位详情
  完整条件依据 → 官方原文 → 保存/准备报名
```

原则：填写页负责“收集”，结果页负责“回答”，详情页负责“证明”。不要让同一页同时承担三件事。

## 3. 两屏填写方案

### 第一屏：去哪儿

- 标题：“你想优先查看哪里的教师招聘？”
- 直接露出常用地区快捷项，不用先点“添加第一个地区”再进入下一层。
- 搜索输入框放在快捷项上方。
- 选中地区后，在同一行出现“只考虑 / 优先考虑 / 也可以考虑”。
- 主按钮文案使用“下一步：填写报考条件”，而不是单独的“下一步”。

### 第二屏：我是否符合

按影响程度排序，而不是按数据库字段排序：

1. 最高学历
2. 专业全称
3. 毕业时间
4. 教师资格状态（按状态展开学段、学科或预计取得时间）
5. 用工偏好（三档，标注“只影响排序与筛选，不影响资格判断”）

底部主按钮写成“查看匹配结果”，并在按钮上方显示一行摘要，例如“杭州优先 · 本科 · 汉语言文学 · 初中语文 · 事业编优先”。

## 4. 结果页推荐布局

### 桌面端

```text
┌──────────────────────────────────────────────────────────┐
│ 为你找到 3 个值得看的机会                 最后核对 10/12 │
│ 1 个初步符合 · 2 个待补信息                              │
│ [杭州优先] [本科] [汉语言文学] [初中语文] [事业编优先] 修改│
├──────────────────────────────────────────────────────────┤
│ [优先机会 1] [待补信息 2] [偏好范围外 3]                 │
│                                                          │
│  初步符合                                  6 天后截止     │
│  杭州某中学 · 初中语文教师                               │
│  📍 杭州 · 余杭区 · 杭州某中学            地图 ↗         │
│  [事业编] [招 2 人] [初中] [语文]                        │
│  ✓ 学历符合  ✓ 专业符合  ✓ 教资符合  ? 户籍待确认        │
│  关键提醒：公告未明确是否限户籍                          │
│  [查看官方依据]                         [保存]            │
│                                                          │
│  其他岗位卡……                                            │
├──────────────────────────────────────────────────────────┤
│ 当前覆盖范围 / 为什么可能不完整 / 已截止与不符合（折叠） │
└──────────────────────────────────────────────────────────┘
```

不建议把宣传型大 Hero 带入结果页。结果页标题应像“决策摘要”，不是再次介绍产品。

### 移动端

- 单列，不做左右分屏。
- 顶部是可横向滚动的筛选标签，尾部固定“修改”。
- 地点和“地图 ↗”保持同一行。
- 一张卡只保留一个主按钮；保存使用图标或次级文字操作。
- 卡片默认展示 3—4 项关键判断，不需要展开才知道为什么。
- 完整官方证据继续进入详情页或底部抽屉。

## 5. 岗位卡片的信息层级

### 第一层：不用点击就必须知道

1. 判断状态：初步符合 / 待补信息 / 建议确认 / 明确不符
2. 报名紧迫度：剩余天数优先于完整日期
3. 学校或报考单元 + 岗位名
4. 地点 + 地图入口
5. 用工形式、学段学科、人数
6. 已通过和待确认的核心条件
7. 一个明确下一步

### 第二层：详情或展开后再看

- 每一条条件的官方原文
- 岗位表行号、附件定位
- 公告版本变化
- 完整时间线
- 地图免责声明
- 数据覆盖和方法说明

## 6. 真实数据与虚拟示例的处理

推荐页面级分隔：

- 若有真实机会：先展示真实机会；示例完全折叠到“体验其他判断状态”。
- 若没有真实机会：第一屏直接说“当前监测范围内暂无正在报名的真实机会”，下一行再说“下面用 1 条虚构岗位演示判断方式”。
- 示例区域使用轻微暖色背景或斜纹水印，卡片只保留一个“示例”角标，不在每个字段旁重复解释。
- 不要把“真实监测事实”和“虚构判断示例”做成视觉权重相同的连续卡片。

## 7. 推荐的视觉方向：可信的未来感

这个产品不适合霓虹、重玻璃拟态或深色交易终端风。教师招聘属于高风险、强依据的决策场景，更适合“可信的未来感”：像现代生产力工具一样克制，但比政务网站更轻、更有反馈。

建议组合：

- 结构借鉴 Airbnb 的“列表比较 + 地点直接可见”；
- 筛选借鉴 LinkedIn Jobs 的结果页顶部筛选，但只保留 4—5 个真正影响决策的筛选；
- 信息密度和操作位置借鉴 Linear 的一致性与克制；
- 视觉语气使用 Open Design 中 `linear-app`、`stripe`、`editorial` 三类系统的交集，而不是套用完整后台模板。

视觉规则：

- 背景使用偏暖的浅灰，卡片白色；主色为深靛蓝或电光蓝，强调色只用于状态和交互。
- 页面标题 28—32px，岗位标题 18—20px，关键数字和截止状态 14—16px，说明文字 12—13px。
- 减少“每一块都圆角卡片”的做法，页面主要层级用留白和分隔线，只有岗位和关键决策需要卡片容器。
- 胶囊标签只承载状态或筛选，不要把普通说明也做成胶囊。
- 动效控制在 160—220ms：筛选结果淡入、卡片轻微抬升、状态切换平滑；不做大面积漂浮和背景动画。
- 图标只负责定位、截止、官方来源、保存四种高频语义。
- 国内受邀环境继续使用本地系统字体或自托管字体，不引入境外字体依赖。

## 8. 三种视角的发散清单

### 产品经理视角

1. “答案优先”结果页：第一屏只回答结果数量、最优机会、原因和下一步。
2. 用工偏好收回画像：在第二屏末尾完成，不让结果页再次提问。
3. 用状态标签切换结果：优先机会、待补信息、偏好范围外、已排除。
4. 真实/示例隔离：页面级明确边界，减少重复免责声明。
5. 每个岗位只有一个下一步：查看依据、补一项、确认问题或查看不符原因。

### 产品设计视角

1. 地点成为首层：位置行与地图入口紧跟岗位标题。
2. 条件可视化：用“✓ 3 项通过 / ? 1 项待确认”替代整段同权重文字。
3. 筛选摘要标签化：结果顶部可见且可快速修改。
4. 渐进披露：先展示决策信息，长证据和覆盖解释后置。
5. 可信未来感：中性底色、强排版、少量电光蓝、轻动效。

### 工程视角

1. 抽象统一的 DecisionCard：访客示例和登录后真实机会共用同一信息骨架。
2. 地图入口由同一个地点模型驱动，在列表卡和详情页复用。
3. 页面根据结果数量自适应：少结果用重点卡，多结果才出现列表/地图切换。
4. 筛选摘要与画像共用同一份状态，修改后原地刷新而不是重新走完整流程。
5. 用功能开关验证新旧布局，埋点只比较“10 秒找到优先机会”“展开依据”“地图点击”“保存机会”等行为。

## 9. 优先级最高的五个方案

| 优先级 | 方案 | 为什么优先 | 关键假设 |
|---|---|---|---|
| P0 | 结果页改为答案优先 | 直接解决页面多、重点不突出 | 用户首先想确认“有没有、哪个最好” |
| P0 | 岗位卡重排并内联地图入口 | 同时解决地点被埋和信息同权重 | 地点是用户第一轮比较的重要条件 |
| P0 | 用工偏好移到第二屏 | 消除完成填写后再次被提问的断裂 | 增加一个紧凑偏好不会显著降低完成率 |
| P0 | 真实与示例页面级隔离 | 降低认知负担并保护可信度 | 用户能更快识别真实数据边界 |
| P1 | 建立可信未来感视觉系统 | 提升第一印象和使用欲望，但不牺牲严肃性 | 用户偏好现代生产力工具，而非传统政务风 |

## 10. 最小验证方式

先不追求完整视觉翻新，做两张可点击高保真稿即可：

1. 现有结果页；
2. “答案优先 + 内联地图 + 用工偏好前置”的新结果页。

让 5—8 名目标用户在不提示的情况下完成三件事：

- 10 秒内指出最值得看的岗位和一条原因；
- 找到岗位地点并打开地图；
- 说清楚用工偏好是否影响资格判断。

同时记录：首次停顿位置、误读真实/示例次数、完成用时、是否需要展开详情才能回答。若新版没有显著改善这四项，再讨论更重的地图分屏或视觉特效。

## 11. 灵感来源与使用边界

- [Figma Dashboard Design Templates](https://www.figma.com/templates/dashboard-designs/)：可用于搜集组件和排版，不建议直接套用数据大屏模板。
- [Open Design Showcase](https://opendesigner.io/showcase)：可参考 `linear-app`、`stripe`、`editorial` 的视觉语气组合。
- [Nicelydone Split View Examples](https://nicelydone.club/examples/tags/split-view)：可参考列表与地图的关系，但当前岗位量不足，不建议默认分屏。
- [LinkedIn：筛选和排序职位结果](https://www.linkedin.com/help/linkedin/answer/a507441/filter-and-sort-job-search-results)：可参考把位置、时间和用工类型放在结果页可见筛选区。
- [Airbnb：搜索房源](https://www.airbnb.co.uk/help/article/421)：可参考结果中直接提供地点和地图上下文。
- [Linear：A calmer interface for a product in motion](https://linear.app/now/behind-the-latest-design-refresh)：可参考一致的操作位置、克制的布局和减少界面噪音。
